# Frontend Agent Guide

适用于 `frontend/**`。同时遵循仓库 [贡献约定](../CONTRIBUTING.md)；开发命令与目录入口见 [README](./README.md)，依赖和构建配置以实际文件为准。

## 区块与依赖

- `frontend/` 是独立 npm workspace，维护自己的锁文件。Studio、产品文档和 SDK 在各自目录构建，通过公开入口消费共享资产。
- 区块以 `modules/` 组织，通过 Hook 调用共享 Client、处理数据与状态，再组合 `components/` 视图。Client 默认遵循 OpenViking 原生 API 契约；Provider 通过 Context 下发通用请求配置，区块可局部覆盖，非标准网关在宿主接入层适配。宿主通过区块接入业务能力，数据与状态 Hook 内置，不提供无头公开接口。区块和组件均可复用框架无关的函数、类型和设计资产；禁止反向依赖 Studio 路由、业务代码和全局状态。
- 按共同完成的交互流程划分区块，共享状态与跨组件联动在区块内维护，不按单个视图组件拆区块。区块 Hook 或宿主负责数据加载、分页与会话；宿主协调不同区块之间的联动。视图组件通过 props 接收数据和状态，通过事件回调表达操作意图。完整页面由宿主组装；认证、账号作用域、路由、权限执行及产品专属流程由宿主提供。
- 新增依赖、图标和资源必须能在公开环境安装与使用。内部 SDK、Starling、私有 IconBox、内部 CDN 和内部路径不进入公共库或示例。迁入已有代码时检查其授权及第三方许可证，沿用仓库既定许可证，变更许可证属于独立决策。
- 日期算术与解析用 `dayjs`。给人看的格式化（月份名、周名、相对时间）用 `Intl`，跟随传入的 locale。发给接口的日期串用 `toApiDate`（`shared/components/date-picker/api-date.ts`），固定输出 `YYYY-MM-DD`；按接口约定传 `'local'` 或 `'utc'` 指定取哪一天，服务端按这个形状校验，其他层需要 `YYYY-MM-DD` 时复用同一个函数。
- React/ReactDOM 保持为 peer dependencies，并从库构建中 externalize；消费者使用自己的 React 实例。重型编辑器、媒体和浏览器专用依赖按需加载，模块导入和服务端渲染阶段应能在没有 `window`、`document` 的环境运行。
- 包导出、类型声明、CSS 和附属资源一起构成消费接口。新增 worker 或其他资源时，验证发布产物及消费端 URL，避免把某个构建工具的源码导入语法直接暴露给消费者。

## 源码目录

- React 包发布名为 `@openviking/react`。源码边界可以先在 workspace 内共享，通过子路径提供消费入口。有独立安装、依赖隔离或独立发布节奏的需求时再拆包。
- OpenViking 请求客户端放在 `packages/react/src/client/`，从 `@openviking/react/client` 交付；客户端本身不依赖 React，同一入口导出的 `OpenVikingProvider` 例外。出现独立于 React 的消费需求时再拆成独立包，并在未安装 React 的项目中验证。仅供单个区块使用的工具留在区块内。业务 Hook 是区块内部实现，不从包根或子路径公开；组件不能使用取数或缓存 Hook。
- 图标的 SVG 源文件、来源与授权放在 `packages/icons/`。React 图标组件放在 `packages/react/src/icons/`，随 React 包从 `@openviking/react/icons` 交付。各框架的封装直接消费同一份 SVG 源文件。构建产物包含图标实现和类型声明，消费者通过 React 包一次安装。
- React 源码的 `components/` 放独立的业务组件（纯视图），`modules/` 放按业务能力划分的 Hook 与组合视图，不提供完整页面。区块内部 Hook 管理数据、状态与操作，组合视图复用 Hook 并组装纯 UI 组件；宿主差异通过服务契约、参数、回调与插槽接入。可独立部署的微应用放在 `apps/`，例如 `apps/workbench-embed/`，消费公开区块与组件，管理挂载、卸载、样式隔离和宿主通信。
- 每个业务组件或区块独占一个 kebab-case 目录，入口文件与目录同名。实现、样式、测试及私有子组件就近放置，例如 `components/<名称>/<名称>.tsx` 和同目录的 `<名称>.css`。区块私有的 Hook、类型和工具留在区块内，不提前提升到公共目录。
- 根入口与子路径分别维护公开导出；业务组件子路径为 `@openviking/react/components/<组件>`，区块为 `@openviking/react/modules/<区块>`，从区块入口导出组合组件与必要类型，内部 Hook 和控制器不公开。不提供 `components`、`modules` 分类聚合 JS 入口。包导出显式列举，内部文件不开放；各入口共享实现，避免重复创建 Provider、Context 或状态对象。同步维护 Rslib 入口和声明路径。
- 被多个组件共用的内部代码放在 `src/shared/`，**不设公开入口**：不进包根导出、不进子路径、不写进 `package.json` 的 `exports`。只有出现第二个真实消费者时才提升到这里；单个组件用到的东西留在该组件目录内。共享代码不得反向依赖 `components/`、`modules/` 或任何宿主契约。
- 内部通用基础件（Button、Input、Modal、Drawer、Tooltip 等）放在 `src/shared/primitives/<名称>/`，不设公开入口；业务内容与专属样式由调用方通过 `children` 或 props 提供。
- 目录按实际内容创建，不预建空目录，也不为单个简单模块增加不必要的转发层。

## 命名

- 名字说明它是什么：目录名为 kebab-case，导出名为对应的 PascalCase；整名不用缩写，例如 `CommandConsole`，不用 `Tui`。
- 同族分组：三个以上共享内部代码的同族组件放在 `components/<族>/<组件>/`，目录名和导出名不带族前缀，例如 `components/auth/email-login-form` 导出 `EmailLoginForm`。
- 公开导出带组件名前缀：写 `FilePreviewLabels`，不写 `Labels`；子组件以父组件名开头，例如 `VikingBotComposer`。
- 一词一义：`entry` 只指文件和目录条目；按钮和入口称 `action`，例如 `FileBrowserActionBar`。
- 私有文件按职责命名：新增文件写 `labels.ts`、`types.ts`，不重复目录名；单个目录超过 20 个文件时，按职责拆子目录。

## 代码写法

- 优先用语法糖代替手写分支，同一件事写得越短越好，比如优先推荐 `??`、`?.`、`??=`、`||=`。

## 样式与交互

- 库样式局部化，类名使用 `ov-` 前缀加 BEM 命名（块 `.ov-file-tree`，元素 `.ov-file-tree__row`，修饰 `.ov-file-preview__button--primary`），主题变量使用 `--ov-ui-` 前缀。消费者无需额外扫描库源码生成 Tailwind CSS，也不承担库的全局 reset；库样式不修改应用的 `html`、`body`、`:root` 或 `.dark`。
- **颜色一律取自主题基线，不要在组件里另写色值。** 包级基线在 `packages/react/src/theme.css`，是一套 `--ov-ui-color-*` 变量（主色、文字、边框、底色、语义色、浮层），取值来自 OpenViking 控制台的设计规范。新写或改动样式时先看基线里有没有对应语义的变量；有就直接用，没有就先往基线里补一条，再在组件里引用。不要在组件 CSS 里写 `#5252ff`、`rgb(0 0 0 / 8%)` 这类字面值——它们不会跟随宿主主题切换，也无法被宿主统一覆盖。
- 组件私有变量用 `--ov-ui-<组件>-*` 前缀，值从基线派生（`--ov-ui-file-preview-accent: var(--ov-ui-color-primary)`），不要重复定义一份色值。只有纯几何量（行高、圆角、缩进）或组件独有的语义（如文件树的层级竖线）才在组件里直接赋值。
- 暗色只认宿主放在 `<html>` 上的 `.dark` 类，不读 `prefers-color-scheme`：系统偏好与宿主实际呈现的主题可能不一致，跟系统走会让组件底色与周围文字对不上。
- 文档站的全局样式、布局和主题覆盖只作用于文档站。CSS 同时提供整包 `style.css`、分类 `components/style.css` / `modules/style.css` 和单个组件或区块的 `<分类>/<名称>/style.css` 入口；JS 不隐式加载样式。各 CSS 入口共用样式源码并可独立消费，区块 CSS 包含该区块及其依赖组件的样式。保留构建中的 CSS 副作用声明。
- 复用区块使用实例内状态和引用。持久化、请求缓存等需要跨实例共享的行为通过明确的 Adapter 接入，避免用全局 DOM ID、事件或 singleton Store 隐式关联实例与账号。
- 状态通过可见文本表达；可操作控件使用合适的语义、键盘行为和焦点样式。

## 国际化与文案

- `components` 与 `modules` 共用类型化语言包和轻量解析机制，当前不引入 i18next、FormatJS 等完整运行时，也不依赖宿主的全局翻译实例。宿主在接入层映射自己的国际化方案。
- 有内置文案的业务组件与区块均使用可选 `locale: 'zh-CN' | 'en-US'`。语言按组件 Props、区块 Props、最近的 `OpenVikingProvider`、默认 `en-US` 的顺序解析；嵌套 Provider 省略时继承外层，显式 Props 可覆盖上层。区块的语言作用域同时覆盖内置视图与宿主插槽。
- 界面译文由所属组件或区块在自己的 `locales/en-US.ts`、`locales/zh-CN.ts` 中维护，不集中建立全库业务词条表。区块仅维护自己的流程文案，复用子组件的默认文案。源文档生成的长内容快照维护源文件与生成流程，不直接修改产物。`packages/react/src/shared/locale.ts` 只管理共同的语言类型、默认值和覆盖规则，不存业务文案、不设公开入口。
- 两种语言保持相同的 key、占位符和格式化函数契约，使用共同类型约束。动态文案使用类型化格式化函数，日期与数字使用 `Intl`；不在 JSX、业务逻辑或 Hook 中散落双语文案分支，不自行扩展复杂模板引擎。复杂语言规则成为实际需求时，再评估成熟国际化引擎。
- 保留已有 `labels` 的逐项覆盖能力：显式覆盖优先于所选语言的默认值，`undefined` 继承默认值，空字符串保留为显式覆盖。嵌套文案逐键合并，覆盖一个字段不能丢失其他默认项。
- 区块自己生成的状态、错误提示优先保存结构化代码与参数，在展示时按当前语言格式化；服务端返回内容、错误原文、AI 回复与用户输入作为内容保留，不自动翻译。应用页面与产品专属文案由宿主维护。
- 语言 Context 位于内部 `src/shared/locale-context.tsx`，与请求 Client 的 Context 和 memo 依赖分离，不从公共入口导出。
- 切换语言只更新展示，不重启请求、清空记录或重置会话与草稿；不将翻译后的字符串或文案对象作为取数、缓存失效的依据。
- 新增或修改语言资源时，同步维护中英文；测试校验 key、字符串占位符与格式化函数参数数量，类型检查约束参数类型。涉及交互时验证语言切换、局部及嵌套覆盖、独立 Hook 和原始内容保留，具体命令遵循下方验证约定。

## 示例与文档

- 顶部导航依次是指南、业务组件、区块和 OpenViking 文档外链，英文站对应 Guide、Business components、Blocks 和 OpenViking docs。指南承载快速开始、国际化和样式；业务组件承载 `components/` 的组件页；区块承载 `modules/` 的区块页。
- 文档按语言组织在 `docs/docs/en/` 和 `docs/docs/zh/`，各语言内按 `guide/`、`components/`、`modules/` 分类，区块归入 `modules/`。
- 简体中文为默认语言，使用 `/ui/` 下的地址；英文使用 `/ui/en/`。新增或修改文档时同步维护两种语言的页面，并在 `docs/sidebar.ts` 登记，中英文侧边栏由它统一生成；保持对应页面路径一致，以支持原位语言切换。可运行示例共用 `docs/docs/_demos/`，不要为翻译复制实现；示例将站点语言映射为组件 `locale`，业务示例内容与文案覆盖由调用者提供。
- 区块分类入口指向该分类的 `index.mdx` 概览，而不是首个区块；侧边栏按路由前缀隔离，仅列出当前分类的概览与详情，并按职责分组。新增分类时同时提供真实内容、概览和导航，不创建空栏目或占位页面。
- 示例从 `@openviking/react` 的公开导出及样式入口导入，不通过相对路径绕过接口。外部 TSX 示例是可运行代码与源码展示的同一事实源。
- 开发与正式文档均通过包导出消费实际库产物。开发模式由官方 workspace 插件启动 Rslib watch；不使用源码 alias 或 TypeScript paths 绕过产物解析，以发现缺失导出、CSS 和打包资源等问题。
- 新增或修改公开能力时，同步检查导出、示例、属性表和导航。手写属性表中的默认值、异步语义和错误行为必须与实际实现一致。
- 示例使用固定、公开的数据和可独立运行的 Adapter；模拟结果应明确标识，截图与输出中不包含真实密钥、内部地址或个人数据。

## 文档写法

适用于 AGENTS.md、README 和文档站页面。读者是集成组件库的开发者：文档回答这是什么、何时使用、怎么用、有哪些参数。

### 业务组件与区块页面

结构沿用 Ant Design，中英文页面的章节、标题和代码块一一对应：

1. 标题写 `Name 中文名`（英文页只写 `Name`），下面一句话简介：它是什么、做什么。
2. `## 何时使用`：1 到 3 条适用场景，必要时写明不适用的情形。
3. `## 引入`：组件的导入路径和样式入口，各一行代码。
4. `## 代码演示`：每个示例一个 `###`，标题是短名词，下面一句说明，再放可运行示例。
5. `## API`：每个公开类型一张表，列为「参数 / 说明 / 类型 / 默认值」，必填项的默认值写「必填」，没有默认值写 `-`。说明用一句话，只讲效果。
6. `## 注意`、`## 主题变量`、`## 常见问题` 按需增加。

- 页面开头直接写简介。`locale`、`labels`、`slots` 各占 API 表的一行，语言解析和文案覆盖的规则只写在 Guide 的「国际化」页。
- `labels` 的键另列一张 `XxxLabels` 表，默认值写当前语言的内置文案。
- 区块页的 API 表包含 `requestOptions`，Provider 与请求配置的规则只写在区块概览页。
- 只写对使用者有用的信息：内部分支和仓库名、设计稿节点、「参考某版本」、评审与完成进度（如「仍是占位」「本期实现」）写进 PR 描述。

### 通用规则

- 单一出处：一个事实只在一处写全，其他位置放链接。
- 用法写在文档站：业务组件和区块的用法、属性表、示例只在 `docs/docs/{zh,en}/` 写一份；组件目录的 README 放一句话简介、公开入口和文档站链接，包 README 放安装、最小示例和文档站链接。
- 只写现状：只描述代码现在的行为。计划、调研、与其他实现的对照和阶段进展放 issue 或 PR，工作稿落地后删除。
- 能查到的不抄：组件清单、目录树、导出列表和命令以 `ls`、`package.json`、`npm run` 的输出为准，文档写明去哪里查。确需列出时，与代码在同一次提交里更新。
- 一条一事：一条 bullet 一个规则或事实，不超过两句；理由不显而易见时，用一句话跟在规则后面。
- 具体名词：抽象词（契约、边界、联动、职责）后面跟具体对象，写出哪个组件、哪个 prop、哪个文件和具体数值。
- 肯定句直述：写应该怎样，例如「请求由宿主发起」；确需禁止时，同时写出该做的事。
- 标点：列表项用冒号连接名称与说明，句内用逗号或句号断开。
- 术语固定：`components/` 下称「业务组件」，`modules/` 下称「区块」，单独说「组件」时泛指这两类；嵌入组件库的应用称「宿主」，同一概念不换同义词。
- 英文页：按英文习惯改写中文页的内容，不逐句直译。

提交前把文档里的默认值、导出名、命令、数量和路径逐条对照代码或命令输出，以代码为准。

改写示例：

- 前：可选 `locale: 'zh-CN' | 'en-US'` 覆盖最近的区块或 Provider；均未配置时默认 `en-US`。业务内容仍由宿主提供。
- 后：FileTree 把宿主提供的行渲染成可展开、可键盘操作的文件树。
- 前：说明文字限宽 200px 并按需省略——它是补充信息，一条长说明会把行拉到几百像素宽，反而让横向滚动更难用。
- 后：说明文字最宽 200px，超出省略，避免长说明撑宽整行。

## 静态部署

- `/ui/` 是组件站的部署前缀。链接与静态资源使用 Rspress 的 base 处理；修改路由或资源路径时检查页面直达、刷新和嵌套路径，不能只检查首页。
- GitHub Pages 每次替换整个站点。组件站产物须与产品文档合并后发布，不能新增一条只上传 UI 产物的 Pages 部署。
- TOS 需要先上传页面依赖的资源，再上传 HTML；无扩展名页面需对应实际 HTML 对象。保留产品文档路径，避免创建遮蔽 `/ui/` 目录的 `/ui` 对象。
- 部署入口与产物合并规则见 [Pages 工作流](../.github/workflows/_docs-deploy.yml)、[TOS 工作流](../.github/workflows/docs-tos.yml)。分支检查通过、正式站发布和 npm 发包是不同结果，交付时分别说明。

## 验证与交付

- JS/TS 文件（含 JSX、TSX）每个文件最多 200 行，不计空行和纯注释行，由 lint 的 `max-lines` 规则检查。
- 按变更选择验证：纯文字改动检查格式、链接和差异；类型、实现或构建配置改动运行 workspace 的格式检查、类型检查和完整构建。命令见 README，CI 环境见 [公共构建 action](../.github/actions/build-ui/action.yml)。
- 格式化与检查只针对本次改动的文件：在 `frontend/` 下执行 `npm run lint -- <改动文件>` 或 `npx prettier --write <改动文件>`，不要用 `--write .`、`--check .` 等扫描整个目录的写法。仓库根与 `frontend/` 存在同名目录（`docs/`、`README.md`、`AGENTS.md`），从错误的工作目录用相对路径会改到本仓库无关的产品文档；格式化前确认工作目录，并检查 `git status` 里没有出现预期之外的文件。
- 用户可见的行为或样式改动，在浏览器中运行构建后的文档并实际操作示例，检查相关的主题、窄屏和失败状态；截图后查看图片，构建成功本身不能证明页面可用。
- 修改包导出、peer dependencies、资源或打包策略时，从真实打包产物验证消费者，包括声明支持的 React 版本，并检查声明、CSS 与 SVG 能在 workspace 外解析；文档开发模式不能代替独立消费验证。
- 修改部署时，验证合并后主站页面仍存在，并检查 UI 深链及静态资源。线上尚未发布或外部检查尚未结束时，报告实际状态。
- 交付前检查最终 diff、`git diff --check` 和工作区状态。`frontend/AGENTS.md` 应由 Git 跟踪；构建产物和临时验证文件保持忽略。

VikingBot 对话是公开无头模块的明确例外：`modules/viking-bot` 导出 `useVikingBotChat`、`useVikingBotSessions` 及必要契约，供 Console 与独立 VikingBot 宿主共同使用；不导出组合组件，不提供 CSS 入口，不从根入口或 Console 入口转导出 Hook。其他模块 Hook 仍按上述内部边界执行。
