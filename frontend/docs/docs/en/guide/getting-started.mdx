# Getting started

`@openviking/react` is the React component library for OpenViking. It provides [business components](../components/) such as a file tree, file preview, command console, conversation, login forms and dashboards, plus [blocks](../modules/) that load their own data.

Mount components in the browser. The package currently supports client-side rendering (CSR) only.

## Install

```bash
npm install @openviking/react
```

`react` and `react-dom` are peer dependencies, at `^18.2.0 || ^19.0.0`. The package ships ESM entries only.

FilePreview and VikingBot render with the optional peer dependency `@ark-design/ui`, and so do FileBrowser and Console, which contain them. For the versions and companion packages, see the Import section of the [FilePreview](../components/file-preview) and [VikingBot](../components/viking-bot) pages.

## Import styles

JavaScript imports do not load CSS automatically, so import the stylesheet you need:

```ts
// The whole library: all business components, blocks and the theme
import '@openviking/react/style.css';

// All business components, or all blocks
import '@openviking/react/components/style.css';
import '@openviking/react/modules/style.css';

// One business component or block
import '@openviking/react/components/file-tree/style.css';
import '@openviking/react/modules/file-browser/style.css';
```

Each entry works on its own and already includes the styles of the components it uses. Icons (`@openviking/react/icons`) need no stylesheet.

## Use a business component

A business component is a plain view: you pass in the data, user actions come back through callbacks, and the component sends no requests. This FileTree renders the rows you give it as a file tree:

```tsx
import { useState } from 'react';
import {
  FileTree,
  type FileTreeRow,
} from '@openviking/react/components/file-tree';
import '@openviking/react/components/file-tree/style.css';

const rows: FileTreeRow[] = [
  {
    kind: 'entry',
    id: 'viking://resources',
    uri: 'viking://resources',
    name: 'resources',
    type: 'directory',
    depth: 0,
    expanded: true,
  },
  {
    kind: 'entry',
    id: 'viking://resources/intro.md',
    uri: 'viking://resources/intro.md',
    name: 'intro.md',
    type: 'file',
    depth: 1,
  },
];

export function Tree() {
  const [selectedId, setSelectedId] = useState<string>();
  return (
    <div style={{ height: 320 }}>
      <FileTree
        rows={rows}
        selectedId={selectedId}
        search={false}
        refresh={false}
        operations={{ select: async (row) => setSelectedId(row.id) }}
      />
    </div>
  );
}
```

FileTree is as tall as its parent, so give the wrapper a height. The example provides no search or refresh implementation, so `search={false}` and `refresh={false}` hide those two entries.

Import rules:

- Import a component and its types from `@openviking/react/components/<name>`, for example `file-tree`; the Import section of each component page gives its exact path.
- The root entry `@openviking/react` also exports the component and its main Props type, such as `FileTree` and `FileTreeProps`; all other types come from the subpath only.
- FilePreview is the exception: it depends on the optional peer `@ark-design/ui`, so it is exported only from the `@openviking/react/components/file-preview` subpath and not from the root entry.

## Use a block

FileBrowser and Console read the OpenViking native API themselves, so place them inside `OpenVikingProvider`, which supplies the service address and credentials. This example uses FileBrowser:

```tsx
import { OpenVikingProvider } from '@openviking/react/client';
import { FileBrowser } from '@openviking/react/modules/file-browser';
import '@openviking/react/modules/file-browser/style.css';

export function Browser({ apiKey }: { apiKey: string }) {
  return (
    <OpenVikingProvider baseURL="https://ov.example.com" apiKey={apiKey}>
      <div style={{ height: 600 }}>
        <FileBrowser />
      </div>
    </OpenVikingProvider>
  );
}
```

- `baseURL` is the service address without `/api/v1`.
- FileBrowser is as tall as its parent, so give its wrapper a height.
- FileBrowser previews file content with the optional peer dependency `@ark-design/ui`, so install it first; see Install above.
- Your app handles sign-in, account scope and routing.
- For the other identity fields, `requestOptions` and the rules of each block, see [Blocks](../modules/).

## Custom error display

FilePreview, CommandConsole, VikingBot and its message list, composer and interaction form, both dashboards, and the FileBrowser, Console and ScopeCascade blocks support an optional `slots.errorFallback: ReactNode | ((reset: () => void) => ReactNode)`. It replaces the entire rendering-error display, so the host can supply its own `className`, `style` and interactions.

```tsx
<FileBrowser
  slots={{
    errorFallback: (reset) => (
      <div className="my-error" role="alert">
        Files are unavailable
        <Button onClick={reset}>Retry display</Button>
      </div>
    ),
  }}
/>
```

- Omitted or `undefined`: inherits the enclosing component or block's setting; without one, the built-in regional message and “Retry display” are shown.
- Nested regions: inherit by default; an explicit child setting takes priority. FilePreview tab `slots.errorFallback` overrides the component-level setting.
- `null`: hides the rendering-error display. Custom content replaces the built-in message and retry button.

A render function receives the failed region’s `reset` action. Calling it clears that region’s error state and renders it again, preserving state outside the boundary without explicitly reissuing business requests. If the cause persists, the fallback appears again. Inherited functions receive the reset action of the nested region that failed.

Changing the slot updates failed displays without retrying or clearing state outside the boundary. The slot applies only to rendering exceptions; ordinary request failures retain each component's existing error-state options. The error boundary itself remains internal.

## Theming

Components read their colors from the `--ov-ui-color-*` variables. The library does not define these variables itself: set them on your app root or any ancestor element and the components use your values; when they are unset, the components use built-in default colors.

```css
.my-workbench {
  --ov-ui-color-primary: #0f766e;
  --ov-ui-color-bg-5: #eef5f4;
  --ov-ui-color-border-2: #d4e4e1;
}
```

Set them on `:root` to apply them to the whole app. Component pages that have a Theme variables section list the variables that component reads.

Dark mode keys off the `.dark` class on `<html>` and never reads `prefers-color-scheme`, because the system preference can disagree with the theme your app actually renders. Once `.dark` is present, the components switch to their built-in dark defaults. The variables you set apply in both light and dark mode, so redeclare them under `.dark` when you need dark-specific values:

```css
.dark .my-workbench {
  --ov-ui-color-primary: #5eead4;
}
```

To adjust a single component, override its `--ov-ui-<component>-*` variables. They are declared on the component's root element, so setting them on an ancestor has no effect; write the override on the component's own selector instead:

```css
.my-workbench .ov-file-tree {
  --ov-ui-file-tree-row-height: 28px;
}
```
