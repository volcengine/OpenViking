# Getting started

Public UI components, composed modules accept optional `locale: 'zh-CN' | 'en-US'`. Local Props override the nearest module or Provider; without a configured language, they use `en-US`. Existing `labels` override individual fields; omitted fields follow the current locale and update when it changes. Hosts still provide business content, slots and callback messages.

OpenViking UI provides React foundations for building AI application interfaces on OpenViking, the context database for AI agents. The workspace includes Rslib builds, bilingual documentation, layered directory conventions, and scoped styles. Applications provide business UI, data, authentication, and workflow orchestration.

The package provides FileTree, FilePreview, Tui, ScopeSwitcher and AgentConnect views, five file-type icons, and two business module placeholders. FileTree, FilePreview and Tui are implemented against their contracts, ScopeSwitcher is a stateless layout, and AgentConnect still renders a fixed-size shell. See the [component overview](../components/) and [module overview](../modules/) for their current scope. Public business Hooks are not implemented yet.

## Run locally

Use Node.js 22.12 or newer. From the repository root:

```bash
cd frontend
npm ci
npm run dev
```

Open the `/ui/` address printed by Rspress. Simplified Chinese uses `/ui/`; English uses `/ui/en/`. The navigation language menu switches between corresponding pages.

The workspace development plugin starts Rslib watch before the documentation server. Documentation examples consume built public exports, rather than source aliases. React and ReactDOM are peer dependencies, supporting React 18.2 and React 19; the documentation application uses React 19.

## Organize application code

- `packages/react/src/components/`: reusable views that receive prepared data through props and report intent through callbacks.
- `packages/react/src/modules/`: two importable placeholder components; business Hooks and composed interactions will follow.
- `packages/react/src/hooks/` and `utils/`: internal shared logic, without public subpaths.
- `docs/docs/en/` and `docs/docs/zh/`: corresponding documentation pages; shared runnable examples belong in `docs/docs/_demos/`.

Keep application-specific workflows and authentication in the application layer. Module Hooks load data through the shared Client; components do not fetch business data or depend on application routing.

## Public entries

The root `@openviking/react` entry currently exports `FileTree`, `Tui`, `ScopeSwitcher`, `AgentConnect`, and the two business module placeholders with their main Props types. `FilePreview` is available from the `components/file-preview` subpath only, because its types depend on the optional `@ark-design/ui`. Subtypes — row types, option types, handles and label bags — always come from the subpaths. `@openviking/react/icons` provides five file-type icons.

There are no aggregate `components` or `modules` JavaScript entries. Business placeholders use individual `modules/<module>` entries:

```tsx
import { FileBrowser } from '@openviking/react/modules/file-browser';
import '@openviking/react/modules/file-browser/style.css';

<FileBrowser locale="en-US" />;
```

Each module's props are settled — request options, controlled state, callbacks, slots and copy — though the placeholder component itself still consumes only `className`, `style` and one label. None of them requires a Provider yet. See [Modules](../modules/) for runnable examples and the full props tables.

Business modules will combine data-loading Hooks with composed views around focused capabilities. Module entries export components and necessary types; data and state Hooks remain internal. Authentication, account scope, routing, permissions, and complete page flows remain with the host. The package exposes no headless business Hooks.

The planned capabilities focus on the personal terminal: `file-browser` combines the directory, search, and preview into one module that coordinates resource selection, result navigation, content loading, and refreshes. Hosts can optionally control the current resource. `console` combines the conversation view and TUI in one panel, coordinating mode switching, the toolbar, and shared context while preserving each mode's session and command state. Agent connection remains a separate capability. Hosts coordinate layout, navigation, and interactions between modules. Product onboarding, resource and Skill import flows, and synchronization settings remain with the host. Experience dashboards and session content attach through the file browser's preview extensions; administration is outside this scope. These interactions are planned; the current module components render placeholders only.

Request configuration is provided through `OpenVikingProvider` from `@openviking/react/client`: `baseURL` plus identity fields (`apiKey`, `accountId`, `userId`, `resourceId`), with the Client assembling the headers. The request client already ships as the `@openviking/react/client` subpath: `createOvClient` over `fetch`, plus `OvRequestOptions`, `OvClient` and `OvClientError`. Module views can override individual fields through `requestOptions`; precedence is local options, then the nearest Provider, then library defaults. An empty `baseURL` means same-origin requests. A standard API needs no per-module Adapter. Hosts adapt nonstandard gateways at the shared request boundary. Data and state Hooks are internal, with no headless public API.

## Styling

Styles use stable class names prefixed with `ov-` and the `--ov-ui-` variable prefix. They do not apply a global reset. JavaScript imports do not load CSS automatically; choose the full, category, or individual stylesheet as needed:

```ts
import '@openviking/react/style.css';
// Or choose @openviking/react/components/style.css
// or @openviking/react/modules/style.css.
// Individual entries: @openviking/react/<category>/<module>/style.css.
```

Rslib emits ESM JavaScript, TypeScript declarations, and CSS into `packages/react/dist/`. Each public stylesheet works independently. Module styles currently cover their placeholders; as composed views land, they must include their component dependencies.

### Theming

Colours come from the package-level baseline `--ov-ui-color-*` (declared in `packages/react/src/theme.css`), aligned with the OpenViking console design system. Every component variable derives from the baseline, so overriding it re-skins everything:

```css
.my-workbench {
  --ov-ui-color-primary: #5252ff;
  --ov-ui-color-bg-5: #f1f2f9;
  --ov-ui-color-border-2: #e1e4f2;
}
```

Dark mode keys off the `.dark` class a host puts on `<html>`, never `prefers-color-scheme` — the system preference can disagree with the theme the host renders. The baseline ships a dark set, so switching `.dark` is enough; override the whole set for exact colours.

To adjust a single component, override its `--ov-ui-<component>-*` variables or target a class directly:

```css
.my-workbench {
  --ov-ui-radius: 4px;
}

.my-workbench .ov-file-tree {
  --ov-ui-file-tree-row-height: 28px;
  width: 320px;
}
```

## Build and check

From `frontend/`:

```bash
npm run lint
npm run typecheck
npm test
npm run build
npm run preview
```

`lint` builds the library, runs Rslint's code-quality and type checks, and checks formatting with Prettier. `typecheck` checks the library, build configuration, and documentation TypeScript projects. `test` builds the library and verifies its public package entries. `build` generates the library and static site; the site output is `docs/doc_build/`.

Pass files or quoted globs after `npm run lint --` to limit formatting and lint targets. Type checking still covers the configured projects. JavaScript and TypeScript files are limited to 200 lines, excluding blank and comment-only lines.

## Deployment

Changes under `frontend/` run the UI checks. On `main`, the existing product documentation deployment includes the UI site under `/ui/` in the same complete site artifact or storage bucket. Package publication uses a separate tag-triggered workflow; local builds and tests do not publish to npm.

## Built-in copy and language changes

Components and modules use local, typed English and Chinese resources with shared lightweight resolution. Translations live with their owners and do not depend on the host’s i18next instance or a translation platform. Undefined entries in existing `labels` inherit the selected language; empty strings remain explicit overrides.

Standalone `useConsole` and `useFileBrowser` accept an optional `locale`, inheriting the nearest Provider and otherwise using `en-US`. Changing it updates library notices, command help and summary titles without restarting requests or clearing sessions and drafts. Server content, original error messages and AI replies keep their original text.

### Language inheritance

Set `locale` once on `OpenVikingProvider`; components, composed modules inherit it. A module's `locale` overrides the Provider for its built-in views and host-supplied slots. A component's explicit `locale` wins over that scope. Nested Providers inherit when omitted and override when specified. With no configured locale, the fallback is `en-US`; `labels` still override individual messages.

The example uses a fixed offline service. Change the three selectors and submit `ov read` to compare generated errors. Language changes preserve requests, records, drafts and server content.
