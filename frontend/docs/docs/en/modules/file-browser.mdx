# FileBrowser

Optional `locale: 'zh-CN' | 'en-US'` overrides the nearest module or Provider; without either, copy defaults to `en-US`. Existing `labels` override individual fields. Hosts provide business content.

Directory navigation, search and content preview as one module. The module loads its own data; the host supplies configuration, the controlled current resource, connection configuration, import interactions and copy.

Directories expand on demand and page; clicking a file loads its preview. The module includes a basic search dialog that submits queries to the native search endpoint and displays results. Directory and preview data Hooks remain internal.

The detail pane uses the same toolbar as standalone FilePreview. Directories provide L0 abstract and L1 overview; text files show their body. Supported files can be edited using the native content read/write endpoints, and the pane reloads after saving. Use `readOnly` to disable editing, import and deletion, or enable `acl` to gate the edit button by the resource permission.

Wiki board links are discovered through resource metadata. The Compile registry is loaded only when a Wiki board opens, and is not needed for ordinary file browsing.

## Basic usage

At the default `viking://` root, FileBrowser follows the console order: user, session, agent, resources, then other directories. A subtree selected with `rootUri` keeps the service order.

The example uses fixed data and makes no network request:

## ACL permission management

Enable `acl` for non-root shared resources under `viking://resources/`. It is off by default and makes no additional ACL requests until enabled. Managers open the existing internal Modal from the permission tag details:

```tsx file="../../_demos/file-browser-acl.tsx" preview

```

- Search and select Users / Groups, grant `read`, `write` or `manage`, change levels and remove grants.
- Increases retain inheritance and save immediately. Reducing or removing an existing grant requires confirmation inside the Modal before creating a restricted boundary. Cancel writes nothing.
- Restoring inheritance lists direct grants that will stop applying, then clears direct grants on confirmation. Saving blocks duplicate submission and closing; failures retain the previous grants and server reason.
- Successful saves refresh directories and preview. Native index updates may be asynchronous; server authorization remains authoritative.
- `fs/ls` entries with `access: 'denied'` cannot be selected or expanded. `access: 'container'` allows expansion to accessible children, without previewing the node. `permission: 'read'` displays a read-only marker.

Requests inherit Provider configuration and `requestOptions`. Grants use native `GET / PUT / DELETE /api/v1/acl`; account directory queries explicitly set `include_credentials=false`. Native `fs/stat` currently omits ordinary users’ effective levels: the fallback only probes management access, never interprets 403 as read or write, and never assumes an administrator from a user ID. Supply `acl.resolvePermission(uri, { client, requestOptions })` for host metadata; adapt non-native gateways in the host transport. Group listing requires account administration access. A resource manager without it sees a retryable failure; `acl.listPrincipals` can supply the host directory.

| `acl` option                                       | Default                           | Behavior                                                                                      |
| -------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------- |
| `true`                                             | `false`                           | Enable native ACL integration                                                                 |
| `readOnly`                                         | `false`                           | Show grants while preventing changes                                                          |
| `resolvePermission`                                | Native metadata and manager probe | Resolve effective `read / write / manage`, or `undefined` when unknown                        |
| `listPrincipals({ type, keyword, page }, context)` | Native account directory          | Return `{ principals: string[], hasMore: boolean }`, using `user:id` or `group:id` principals |
| `onChange(report)`                                 | —                                 | Notify after a successful save; the return value does not affect saving                       |

`labels.acl` overrides individual Modal strings; omitted keys inherit the locale. Changing language retains pending confirmation without reloading grants. The host owns identity and scope; the server enforces access. Standalone `FileTree` / `FilePreview` consumers compose permissions through row state, title and action slots.

## Scope

The module includes the file tree, file preview and top entries. The command panel belongs to `console`.

## What the module owns

- Directory, current URI and preview loading are coordinated inside the module: selecting a directory loads its preview, and switching resources drops stale requests. The host can navigate to a resource through `uri`.
- Refreshing the affected directory and preview after a save, rename or delete.
- The layout of the search, directory and preview area, including the draggable divider between the tree and the detail pane. The tree starts at 352px, resizes between 200px and a cap that leaves the detail pane its readable width, and the arrow keys work once the divider has focus.
- The top connection and import entries, search entry and refresh control, plus per-row state such as uploading progress, conflicts and retention settings.
- The preview tabs. Which tabs a resource has follows from the resource itself, so the host does not supply them.
- System metadata inside the body. The `MEMORY_FIELDS` comment at the end of a memory file is an internal field the server writes, not body text: a default read has the server strip it, and when a host turns the request into a raw read (`raw=true`) through a custom transport or a gateway it comes back verbatim, so the module applies the same rule once more — only the block that ends the file counts, a same-shaped comment in the middle survives, and it applies to the memory namespace only. "The end of the file" is decided by whether the end was actually read: a first page short of the preview cap is the whole file, while a full one reads the whole file again, strips, and applies the cap itself — so a body comment ending the first page is never mistaken for a trailer, and a trailer cut off before its closing marker is still recognised. Line boundaries, whitespace and word characters all follow the server's (Python's) rules rather than JS's `split('\n')` / `trim()` / `\b` — the sets differ, and copying JS's would delete body text the server kept on the default read path.
- The search entry reuses the FileTree toolbar and opens the internal placeholder dialog. Submitting a query calls `/api/v1/search/find`.

## What the host owns

- Request configuration through the Provider, overridable per module through `requestOptions`.
- Sign-in, account scope, routing and permissions.
- Connection credentials and product-specific import flows, supplied through `agentConnect`, `onImportResources` and optional `renderImportResources`.

## Entries and toolbar

The search dialog is a placeholder: query submission, loading, errors and results are supported; filters, pagination, result navigation and shortcuts are deferred. A TODO marks the implementation, which has no separate export. The demo answers the same native endpoint through an offline adapter: enter `profile` for results or `error` to trigger a simulated failure and resubmit to retry.

The module includes connection and import entries above search and refresh. The host supplies `Popover` and `ResourceMenu` below. Its default native button is the popover's direct child, allowing it to attach its ref and event handlers for positioning:

```tsx
import { FileBrowser } from '@openviking/react/modules/file-browser';
import '@openviking/react/modules/file-browser/style.css';

<FileBrowser
  locale="en-US"
  agentConnect={{ apiKey: 'demo-api-key', locale: 'en-US' }}
  renderImportResources={(trigger) => (
    <Popover content={<ResourceMenu />} trigger="click">
      {trigger}
    </Popover>
  )}
/>;
```

Providing `agentConnect` enables the connection entry and its drawer, which slides in from the right. Omitting it hides the entry. `renderImportResources(trigger)` receives the native button with its default icon and label; wrap it or return a replacement node. Replacement nodes own their interactions. For click-only interactions, `onImportResources` enables the default import button without a renderer. Wrapping the default button preserves that callback; returning `null` hides the entry. Omitting both `onImportResources` and `renderImportResources` hides the import entry. A single entry has no divider, and nothing renders when both entries are hidden. Use `labels.entries` to replace entry and drawer copy.

For a click callback without custom rendering:

```tsx
<FileBrowser locale="en-US" onImportResources={openImport} />
```

## Preview actions

The header uses Preview / Source, an edit icon and a More menu. Copy content lives in the menu; Copy path stays beside the breadcrumbs. ACL management is available in the permission tag details.

`previewActions` contains only optional boolean visibility flags. Every flag defaults to showing the operation **when the resource supports it**; `false` hides it and `true` grants no extra capability.

| Flag          | Applicability                                                                                                                 |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `copyPath`    | Any preview with a path; rendered beside the breadcrumb.                                                                      |
| `viewSwitch`  | Formats supporting both preview and source; unavailable for images/video and system directories.                              |
| `edit`        | Writable, supported text files; never direct experience files, system resources or L0/L1 summaries.                           |
| `copyContent` | The current text preview or directory summary, including any preview truncation; no binary media or system directory content. |
| `download`    | Files: downloads original bytes through the native content endpoint.                                                          |
| `history`     | Direct user experience files and registered Compile resources. Nested experience files do not inherit this operation.         |
| `configure`   | Compile target root directories only. Settings remain viewable in read-only mode.                                             |
| `importPack`  | Writable directories in the native user/resources namespaces; not a file's parent inferred from file permissions.             |
| `exportPack`  | Files/directories in supported user/resources namespaces, excluding native internal control files.                            |
| `delete`      | Manageable files excluding the browser root, system files and derived summaries. Deletes a file, not a preview tab.           |

Compile ownership comes from target metadata/catalog entries and uses the nearest owning target, with path segment boundaries. A child directory receives history, while only a target root receives configuration.

The module executes these workflows itself:

- History reads `/snapshot/log` scoped to the resource (up to 500 recent snapshots), or `/snapshot/versions` for a Compile output file (up to 100 retained versions). Text revisions load through `/snapshot/show` with `raw=false`; this view does not restore versions.
- Configuration reads `/compile/config` and saves the native source directories, skill, instructions, automatic updates and daily/weekly schedule through `/compile/config/update`.
- Import uploads a `FormData` file through `/resources/temp_upload`, then calls `/pack/import`. Failure retains the selected file; retry uploads it again because the temporary ID is consumed. Export calls `/pack/export` and saves the returned bytes as `.ovpack`.
- Delete opens the confirmed design's dialog, then calls `DELETE /api/v1/fs?uri=...&wait=true`. Failure retains the dialog and allows retry; success selects the parent through `onUriChange` and refreshes the tree. Directory deletion is not built in.

All paths above use `/api/v1`. Requests prevent duplicate submissions and abort on account/resource changes or unmount. API success remains success if a later refresh fails. Language changes preserve dialogs, selection and drafts without restarting requests.

Flags control default presentation. `readOnly` disables writes, including configuration saves; with `acl`, editing/import/configuration writes require `write / manage` and deletion requires `manage`. Without ACL, the module makes no additional permission probe; the server always enforces authorization.

```tsx
<FileBrowser
  previewActions={{
    edit: false,
    delete: false,
    importPack: false,
    configure: false,
  }}
/>
```

`previewSlots` supports three extensions; dashboard content tabs are unaffected:

- `actionItems`: replace the command list with the same grouped array as component `actions`, or a `(context) => FilePreviewActionItems` factory. Reuse, append or reorder `context.defaultActions`, for example `context => [...context.defaultActions, [hostAction]]`. Each command requires `key / icon / label / onClick`, with optional `disabled / className`. Pending commands prevent duplicate invocation; failures show an error and allow retrying.
- `extraActions`: append nodes to the default toolbar, hidden while editing.
- `actions`: a node or `(context: FileBrowserPreviewActionContext) => ReactNode` replacing the entire action area; `null` hides it. Custom renderers provide Save/Cancel and appended actions themselves.

The context includes preview state, path-copy and editing methods, `defaultActions`, plus `canDelete` and `deleteFile()`, which opens the same native confirmation. Read-only mode and ACL restrictions remain effective; hiding a default button does not revoke its supported capability. Copy path and the permission tag remain independent of this slot. Slots grant no permissions; hosts provide copy and feedback for custom controls.

Import `FileBrowserPreviewActions`, `FileBrowserPreviewActionContext` and `FileBrowserPreviewSlots` from `@openviking/react/modules/file-browser`. The basic demo switches between built-in, appended, custom, hidden and individual-control modes and can simulate deletion failure. History, configuration and ovpack use simulated native API responses; exported demo bytes are not a valid backup.

Override native workflow copy with `labels.workflows` (`FileBrowserWorkflowLabels`); omitted keys inherit the selected locale.

## Tree width

A draggable divider sits between the tree and the detail pane: drag it sideways to resize the tree, or focus it and use the arrow keys, 16px at a time.

- 352px by default, matching the design; 200px minimum, below which only icons stay legible.
- The cap is the smaller of 520px and the container width minus 320px for the detail pane and 24px for the divider. A host that puts the module in a narrow column narrows the tree rather than crushing the detail.
- Dragging changes the width of the current instance only and writes nothing to `localStorage`: width is layout, and whether to remember it is the host's decision.

The module owns the width and publishes it as `--ov-file-browser-tree-width` on the container: read it to mirror the layout elsewhere, but overriding it does not change the actual width, because a drag writes straight back to the same variable. To fix the width, wrap the module in a sized container and let its width cap the tree.

The divider's accessible name comes from `labels.resizeTree`; it follows locale and can be overridden.

## Failure states

"Could not read" and "read an empty result" are different, and the module shows them differently:

- When a listing fails, the tree shows a failure row with a retry instead of "no files". The root is no exception — painting it as empty would make a 403 look like a directory that simply has no content.
- When the preview fails, the detail pane shows a failure state: `labels.error` as the conclusion, the server's own message as the reason, and `labels.retry` as the retry. A selected resource that cannot be read never falls back to the empty-state artwork.
- The empty state appears only when nothing is selected.
- Search failures retain the endpoint reason in the dialog. Resubmit the same query to retry; closing cancels the request and clears the draft.
- A directory's two summary levels can fail independently. A failed level keeps its reason instead of becoming an empty body — an empty body means "not generated yet", which differs from "could not load" (a backend fault or missing permission); when both levels fail the whole preview enters its failure state. Without a server message the copy falls back to `labels.summaryFailed`, so that line follows the interface language too.

A retry reloads the listings and the current preview together — after an external change, reloading only the tree would leave the detail pane on stale content.

## Built-in dashboards

Discovery and configuration matching use URIs resolved by the native API in the current authenticated scope, including `viking://~/...` roots and Wiki child-file aliases. Dashboard URIs and host callbacks keep the supplied spelling. The example controls switch between canonical and `~` URIs for the same file.

User `memories/experiences` directories and their direct Markdown files expose the experience dashboard. Wiki detection uses compile configurations or the `compile_target=true` resource marker, including descendant files/directories. Resource metadata wins over a missing registry. Ordinary resources have no Wiki tab; an identified Wiki retains its board when it has zero conflicts.

Tree indicators open the board directly; preview tabs return to file content. FileBrowser's `style.css` includes both boards. See [WikiDashboard](../components/wiki-dashboard) and [ExperienceDashboard](../components/experience-dashboard) for native coverage and host data integration.

`dashboardKinds?: readonly ('wiki' | 'experience')[]` enables both kinds by default; an empty array disables discovery and entries. The host applies product permissions. For example, `dashboardKinds={['experience']}` disables Wiki entries and compile discovery requests. Resource access remains enforced by the server.

`renderDashboard?: (dashboard: FileBrowserDashboard) => ReactNode` integrates gateway data or replaces the composite view; a nullish result keeps the native view. The descriptor contains `kind`, `uri`, and optional Wiki `pendingConflicts`, `isRoot` and the owning `targetUri`.

`labels.dashboard` overrides both tab titles, the three tree action names and discovery failure copy. Inner board copy is customized through each board's own `labels`, supplied through `renderDashboard` when composing FileBrowser.
