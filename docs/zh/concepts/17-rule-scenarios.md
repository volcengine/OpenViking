# 规则（Beta）

Rule 是 Agent 在特定条件下必须遵守的持久强约束，例如行动义务、禁止项和边界。OpenViking 将规则材料批量编译为可独立理解的规则，再根据当前任务召回适用规则，供 Agent 在行动或回答前核验。

当前 Beta 面向主动导入和按需召回。普通会话提交不会自动触发规则编译，也没有在每条用户消息或新会话开始时强制注入规则的内置流程。

## 与其他上下文类型的区别

| 类型 | 回答的问题 | 示例 |
| --- | --- | --- |
| Resource（资源） | 有哪些原始资料可查阅？ | 协议原文、代码仓库、技术规范 |
| Memory（记忆） | 已知哪些事实、偏好和经验？ | 用户偏好简洁回答、项目采用某个框架 |
| Skill（技能） | 如何完成这类任务？ | 仓库审查步骤、报告生成方法 |
| Rule（规则） | 在什么条件下必须做什么或禁止做什么？ | 声明开源的仓库必须提供可定位的许可证文本 |

Rule 的优先级高于普通 Memory。它是一种独立的上下文类型；虽然存储在用户的 `memories/rules/` 下，但使用专门的编译和搜索接口。把协议或规范作为 Resource 导入，只保存了资料，还需显式编译其中的强约束。

偏好、建议、事实、示例和单次任务不应提升为 Rule。编译也不能把原文的“建议”改成“必须”，或弱化“必须”“禁止”。

## 适用场景

| 场景 | 规则来源 | Agent 如何使用 |
| --- | --- | --- |
| 法律协议核查 | 用户提供的协议义务、禁止事项与例外 | 根据具体审查对象和已知事实召回约束，再核对文本或计划动作 |
| 代码规范检查 | 团队开发规范、代码审查要求 | 根据当前仓库、修改内容和执行阶段召回规则，检查拟提交的变更 |
| 开源许可证核查 | 用户提供的许可证要求 | 读取仓库声明和许可证文件，核对触发条件并记录证据 |

例如，输入“仓库声明自己是开源项目时，必须提供明确、完整且可定位的项目许可证文本”，可以形成：

| 字段 | 示例 |
| --- | --- |
| `content` | 仓库声明自己是开源项目时，必须提供明确、完整且可定位的项目许可证文本。 |
| `applies_when` | 仓库声明自己是开源项目。 |
| `exception` | 空字符串：原文没有明确例外。 |
| Scenario | 项目许可证核查 |

主题相似不等于条件成立。Agent 必须依据可读取的材料核验条件；规则已经满足时，它仍然适用。

## 规则如何组织

一条 Rule 保存一个可独立更新或撤销的完整约束，包含 `content`、适用条件 `applies_when`、例外 `exception`、来源与原文证据，以及稳定标识 `atomic_id`、版本 `revision` 和状态 `status`。空 `applies_when` 表示除例外外均适用。

Scenario 描述规则可能适用的实际情况，用于分组和召回，例如“项目许可证核查”。它不是来源文档的标题：同一份文档可以产生多个 Scenario，多份资料也可以复用同一 Scenario。

```text
viking://user/<user_id>/memories/rules/
└── repository-license/
    ├── abstract.md          # Scenario 描述
    └── project-license.md   # 完整 Rule 记录
```

## 编译流程

```text
规则文本、文件、目录或 URL
    → 读取已有资源，或解析并导入新来源
    → 召回已有 active / paused 规则
    → Compiler 提炼约束并生成变更计划
    → 校验结构、目标、原文证据和旧要求保留情况
    → 写入 Rule / Scenario，异步刷新索引
```

Compiler 保留约束强度、条件、例外、阈值和单位，并拆分可独立维护的规则。同一规则的演进更新原记录，完整替代会创建新标识并归档旧记录；已有规则完整覆盖输入时无需重复写入。关键歧义或被拒绝的输入会记录原因，不写入 Rule。

编译接口先返回后台任务。任务完成后检查实际变更；规则写入对应的索引任务可能仍在处理，使用前也要确认该任务完成。具体步骤见[规则校验（Beta）](../workflows/02-rule-validation.md)。

## 搜索与执行流程

```text
Agent 提交任务目标、对象、计划动作和已知事实
    → 语义召回可能相关的 Scenario
    → Jev 过滤高置信度无关的 Scenario
    → 读取其中的 active 规则，判断适用条件与例外
    → 返回结构化规则和完整的约束文本
    → Agent 逐条核验并约束行动或回答
```

搜索默认返回适用分数达到 `0.65` 的规则，公开接口不设置固定 Top-K。非空适用条件下，例外分数达到阈值且严格高于适用条件分数时才否决；空适用条件下，例外达到阈值即否决。

Jev 未配置、不可用或返回无效结果时，受影响候选会放行。Rule 判断失败时返回 `judge="pass"`、`probability=1.0` 和 warning；这个分数表示放行，不是估算概率。Agent 仍需核验条件和例外。

`rendered` 提供应用步骤和完整规则块，可交给 Agent。搜索判断的是“规则是否适用”；是否满足、违反或证据不足，由 Agent 对照任务事实判断。空搜索结果不能证明规则库没有相关约束；`delivery.complete` 也只表示命中规则完整交付，不保证全库召回。

## 生命周期

| 状态 | 编译候选 | 搜索候选 | 含义 |
| --- | --- | --- | --- |
| `active` | 是 | 是 | 启用 |
| `paused` | 是 | 否 | 暂停，保留规则，不安排到期清理 |
| `archived` | 否 | 否 | 逻辑删除，保留期结束后可被清理 |

用户明确要求暂停或禁用时使用 `PAUSE`；恢复暂停规则使用 `RESTORE`。删除、丢弃或移入回收站才使用 `ARCHIVE`。`UPDATE` 保留原有状态。当前编译接口不能恢复 archived 规则。

归档记录保存 `archived_at`，重复归档不重置时间。默认启用定期清理，保留期为 30 天；实际物理清理发生在保留期结束后的扫描中，配置见[服务端 Rules 配置](../configuration/01-server.md#rules)。
