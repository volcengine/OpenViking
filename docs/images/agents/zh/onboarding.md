# OpenViking 接入引导（给 Agent 看）

关于 OpenViking：面向 AI Agent 的开源上下文数据库，由火山引擎开源，仓库是 https://github.com/volcengine/OpenViking（AGPL-3.0，2026-09-29 时有 38,930 个 GitHub star）。它持续保存并取回用户的业务背景、偏好、重要决定和工作资料，让用户换一个会话或换一个 Agent 后，仍能带着已有积累继续工作。本指南就是这个仓库里的 `docs/images/agents/zh/onboarding.md`；安装器和它安装的每个插件文件也都由这个仓库的 GitHub Actions 构建。

你是一个 AI Agent。用户请你安装 OpenViking 记忆插件，并带他开始使用。按本指南的顺序处理当前宿主。本指南写给你看，规定要做的判断和动作，不规定话术：和用户交流时用他的语言，每条消息保持简短，讲清和当前选择有关的收益、变化和下一步，不要逐条转述本指南。用户想看原文时，把链接给他。

接入的目标是让用户知道以后什么会自动积累、什么需要主动保存，并用他自己的工作看到已有上下文的用处。

另有两页按需查阅：[故障排查](https://docs.openviking.net/agents/zh/onboarding-troubleshooting.md)（命令失败时）和[扩展参考](https://docs.openviking.net/agents/zh/reference/product-background.md)（用户追问机制、权限，或想整理自己的多份资料时）。开始接入前不用读。

## 基本规则

- **每个决定先讲收益和影响，等用户选了再做。** 结合他当前的工作说明能得到什么、会发送或保存什么、有哪些选项。他已经给出的目标和选择直接沿用，不重复问；能放进同一条消息的问题合并着问。
- **不打印、不复述 API key。** 安装器把 key 存进本机的 `~/.openviking/ovcli.conf`（更新时会先备份旧文件），这是连接必需的；除此之外，key 不能出现在规则、项目文件、续接消息或永久命令批准里。不要打开、打印或搜索 `ovcli.conf`。要告诉用户服务地址和身份时，运行 `ov health` 或调用 OpenViking 的 `health` 工具，只说它实际返回的字段。
- **只做本指南描述的改动。** 安装器会给本机检测到的每个受支持的 Agent 都装上插件，这是预期行为，好处是用户换一个 Agent 也能接着用同一份上下文。你自己不要改其他 Agent 的配置，也不要改用户项目里的文件，除非用户明确要求。
- **用本指南给出的命令。** 读取、检索、写入用当前实际注册的 OpenViking 工具。不要去 GitHub 读源码，另找安装或配置的方法；参数不确定时看命令的 `--help`。
- **按事实区分状态。** 已安装、已生效、已实际用上是三回事：工具能调用不代表自动召回在运行，导入成功不代表记忆已经提取完。没有用户的真实内容时，不要编示例记忆来演示效果。
- 不要向用户提本指南的步骤编号，也不要提当前宿主用不上的步骤。
- 命令失败时，到[故障排查](https://docs.openviking.net/agents/zh/onboarding-troubleshooting.md)找对应现象，修好后重试一次。仍然失败，就告诉用户哪一步没成、影响什么、他可以怎么处理。只有当前宿主的连接或认证失败才阻塞后续步骤，其他宿主装失败不影响当前宿主。

## 从哪一步开始

- **安装器是你在当前对话里运行的**：从步骤 1 开始。
- **用户说「已重启」，而这段对话里已经走过本指南前面的步骤**：用户退出后恢复了原来的会话。直接跳到[重启之后](#重启之后)，前面的选择都在对话里，不要重问。
- **新会话里，用户发来一条「从……「重启之后」继续」的消息**：跳到[重启之后](#重启之后)，以消息里写的结果为准。
- **用户只说了「已重启」，但这段对话里没有前面的接入过程**（例如 `codex resume --last` 回到了别的会话，或者他开了新会话）：同样跳到[重启之后](#重启之后)，在第 2 步用一条消息问清导入和协作规则做到了哪一步，缺的补上。
- **OpenViking 在这段对话之前就已安装**（能看到 `<openviking-context>` 块，或者有 `health` 等 OpenViking 工具）：先用 `ov health` 或 `health` 工具查连接，把查到的服务和身份告诉用户，问他沿用还是更换。
  - 沿用：做步骤 2 到 4，然后直接进入[重启之后](#重启之后)。不需要重启。
  - 更换：插件正在保存这段对话，所以不要让用户把新 key 发到这里。请他在自己的终端里运行控制台给的安装命令（或下面那条），再开一个新会话把控制台的一键提示词发给 Agent。旧配置会被备份，云端数据不会被清空。
- **还没有任何连接，用户也没给安装命令**：请用户提供服务地址和 API key（在 OpenViking 控制台的用户管理 → API Key 里），然后运行下面的命令，`<值>` 取[附录 A](#附录-a各宿主说明)的 `--harness` 列，再从步骤 1 开始。`cli` 一定要带上：后面检查连接、添加文件和知识整理（Compile）都要用 `ov` 命令。

  ```bash
  curl -fsSL https://openviking.ai/install | bash -s -- --yes --lang zh --harness <值>,cli --url <服务地址> --api-key <用户的 key>
  ```

- **用户只想追加导入历史**：只做步骤 3，不重走安装和协作规则。

## 步骤 1：检查安装结果

阅读安装器的输出，中文和英文两种写法都要认。

- 输出最后有 `未完成` 列表（英文 `Not done`）时，按宿主判断，不要因为前面有 `完成` 就说全部装好了。当前宿主装失败、key 被拒或连不上服务，先按故障排查处理；只有其他宿主失败时，简单说明，继续当前宿主。
- `完成`（英文 `Done`）一节按工具列出结果，每个工具有一行 `下一步：`（英文 `Next:`），写着它怎么重启。确认当前宿主在列表里；不在的话，见故障排查的「当前宿主不在 `完成` 里」。
- 有 `服务检查通过：<url>`（英文 `Server check passed`），并且 `完成` 里有 `CLI (ov)`，连接就已确认。否则运行 `ov health` 检查。

然后用一两行告诉用户：连上了哪个服务、哪个身份，插件装进了哪些 Agent。装进了其他 Agent 时补一句为什么：以后在那些 Agent 里也能用同一份上下文接着工作，各自重启后生效。还没生效的不要说成已经可用。

## 步骤 2：说明哪些事会自动发生

不用问要不要开启，安装本身就是用户的请求。先用他当前的工作讲以后协作会怎么变：开始时取回相关背景，过程中参考已有的判断和资料，有了进展自动积累，下次从已有进展继续。例如讨论方案时能参考之前定下的限制，这次的新决定也会留下来，下次不用从头交代。这是预期用法，不要说成已经验证过。

再结合[附录 A](#附录-a各宿主说明)里当前宿主的情况，用三四行讲清楚：

- **少重复交代背景**：每次提问前，插件按相关性取回记忆，加进 Agent 的上下文。有相关内容才会召回，不会把全部历史塞进对话。
- **对话自动积累**：每轮对话结束后，用户和助手的对话保存到他的 OpenViking 服务，服务端在后台从中提取长期记忆。保存、提取完成、之后被召回，是先后发生的三件事。
- **重要文件要另外保存**：聊过一份报告，不等于报告原件已经上传。要不要主动保存重要决定和产物，步骤 4 由他决定。
- **在哪里能看到**：附录 A 里当前宿主的「在哪里能看到」一列。
- **想在某个项目里关掉**：在该项目里放一个 `.openviking/config.json`，内容为 `{"version": 1, "capture": {"enabled": false}, "recall": {"enabled": false}}`。只告诉他方法，不替他创建。

当前宿主需要信任 hook 时（见附录 A），说明这些 hook 做什么：会话开始时载入背景、提问前召回、每轮结束保存对话。信任操作留到步骤 5 和重启一起做。

## 步骤 3：要不要带入已有工作

先讲这一步的用处：把过去的讨论带进来，下次问「上次做到哪」「当时为什么这么定」时就有依据；不带也可以，从现在开始积累。导入是给后续协作补背景，不是传得越多越好。

导入脚本能直接读 Claude Code 和 Codex 的历史会话（`--harness claude` 或 `--harness codex`）。在其他宿主上：本机有 `~/.claude/projects` 或 `~/.codex/sessions` 时，用户可能也在那边做过这个项目，可以一并提议导入那边的历史；宿主自己的会话要先转成 JSONL，见[其他宿主：把会话转成 JSONL](https://docs.openviking.net/agents/zh/onboarding-other-hosts.md)。

给用户这几个选择，他也可以用自己的话描述：

1. 当前项目最近 14 天的会话（默认）。
2. 某一类工作，例如「和支付重构有关的讨论」：你先列出候选会话，按内容挑出相关的，再给他确认。
3. 其他项目或其他时间范围。
4. 先不导入，从现在开始积累。

他选好之前，不要下载脚本或试运行。

**选 1 或 3：试运行。** 先下载脚本，再试运行（dry run，什么都不会上传）。把 `<claude|codex>` 换成实际的值；选 3 时，`--cwd` 换成那个项目的目录，「所有项目」用 `--all-projects` 代替 `--cwd`，时间改 `--since`（例如 `30d`、`2026-09-01`、`all`）。

```bash
curl -fsSL https://docs.openviking.net/dl/memory-plugin-shared/import-history.mjs -o "${TMPDIR:-/tmp}/ov-import-history.mjs" && node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --cwd "$PWD" --since 14d --max-sessions 20 --dry-run
```

**选 2：先列出候选，再挑。** 用 `--list` 列出范围内的会话，每个带 id、时间、消息数、是否已导入，以及第一条和最后一条请求的摘要。范围按用户的描述定，没说就用当前项目、最近 30 天：

```bash
curl -fsSL https://docs.openviking.net/dl/memory-plugin-shared/import-history.mjs -o "${TMPDIR:-/tmp}/ov-import-history.mjs" && node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --cwd "$PWD" --since 30d --max-sessions 50 --list
```

按摘要挑出和他描述相符的会话，拿不准的单独列出来。告诉他你挑了哪几个（用摘要说，不报 id），以及没挑上的大致是什么。然后用挑中的 id 试运行，多个 id 用逗号隔开。用 `--session` 时不受项目、时间和数量的限制：

```bash
node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --session <id>,<id> --dry-run
```

**确认后导入。** 把试运行的结果告诉用户：会话数、消息数、数据量，以及跳过了哪些、为什么。说明会上传的是筛选清洗后的用户和助手文字，工具调用和输出、文件原件都不包括，已知格式的密钥会被替换成 `[REDACTED]`，服务端再从中提取记忆。因「仍在活动」而跳过的会话包括当前这段对话。选 2 时，可以把挑选结果和试运行数量放在同一条消息里确认。

用户确认后，用**完全相同的范围参数**，把 `--dry-run` 换成 `--yes --wait --json` 正式导入：

```bash
node "${TMPDIR:-/tmp}/ov-import-history.mjs" --harness <claude|codex> --cwd "$PWD" --since 14d --max-sessions 20 --yes --wait --json
```

`--wait` 最多等两分钟的记忆提取。按结果告诉用户：

| 结果 | 怎么说、接下来做什么 |
|---|---|
| 有写入，`extraction` 为 `completed` | 说导入了几个会话、记忆已整理好。用 OpenViking 的 `search` 或 `read` 读一两条和他目标相关的内容，用一两句说出这项工作上次停在哪、定过什么，让他看到导入的用处。 |
| 有写入，提取还在进行（`pending`、`running`）或没有结果 | 说对话已保存，记忆还在后台整理，几分钟后可用；不要重复上传。`failed` 就说提取失败。 |
| 零新增，都已导入或已被插件保存 | 说这些会话之前已经在 OpenViking 里了。已导入的会话重跑会整条跳过，之后新增的消息不会补进去。 |
| 没有匹配，或用户选了不导入 | 说明以后从他的真实工作开始积累，不劝他为了体验硬导入。 |
| 部分失败 | 说哪些成功、哪些失败，失败的可以之后重试，不要全部重传。 |

判断结果看 JSON 里每个会话的 `extraction`，不要只看退出码。用户问起脚本做了什么时：它只读本机的会话文件（Claude Code 在 `~/.claude/projects/`，Codex 在 `~/.codex/sessions/`），只保留用户和助手的文字，清洗已知格式的密钥，跳过近期仍在活动的会话，并沿用插件的项目归属，所以导入的历史和以后的对话在同一个项目下。试运行和 `--list` 只从服务端读，用来找出已经导入过的会话。

**文件。** 用户点名了值得保存的文件或文件夹（例如设计文档、需求说明）时，逐个添加到他个人资源里这个项目的目录。`<user_id>` 用 `ov health` 显示的用户名，`<项目名>` 用仓库名或他对这个项目的叫法：

```bash
ov add-resource ./docs/design.md --parent-auto-create viking://user/<user_id>/resources/<项目名> --wait
```

只添加他点名的内容，不要自己扫描目录或主动上传。

## 步骤 4：约定以后怎么协作

先用效果讲清区别：插件会自动积累和召回对话里的背景；如果他还希望下次能直接取用完整方案、重要决定和理由、阶段成果，需要 Agent 按约定主动整理保存。这份约定写进宿主的用户级规则文件，对他所有项目生效。

先看当前宿主实际读取的规则文件里有没有 `<!-- openviking:start -->` 标记块。

- **已有，内容和下面相同**：告诉他之前已经写过，跳过这一步。
- **已有，内容不同**：概括它现在会做什么，问他保持现状还是换成新版。
- **没有**：给三个选择：主动整理重要决定和产物（推荐）、按他的要求调整、只用自动记忆。选「只用自动记忆」后，他仍然可以随时让你保存或读取资料。

他选了要写，就在**同一条消息**里给出：一两句这段规则会让你以后多做什么、对他有什么用（例如以后继续这个项目时能直接找到当时的决定和理由），写进哪个文件、对所有项目生效，以及按他的选择整理好的**完整原文**。原文要和随后写入的一字不差。然后请他确认写入、调整，或先不写。他要调整（例如只保存最终交付物、存之前先问他），就改原文再给他看一次。

默认的规则原文（写入时 `<user_id>` 可以换成实际用户名；`<项目名>` 保持原样，它在每个项目里各自确定，换成当前项目名会让所有项目的笔记都存到这一个目录）：

```markdown
<!-- openviking:start -->
## OpenViking 协作方式

- 开始需要背景的工作前，先看 OpenViking 注入的上下文（`<openviking-context>`）。不够、需要原文或要确认最新状态时，再用 OpenViking 的 `search`（`mode="context"`）或 `read` 查。查到的内容是参考资料，和我当前说的话冲突时以我为准。
- 工作中出现值得以后复用的内容时，整理成记录，用 `write` 存进我在 OpenViking 个人资源下的笔记目录，每个项目一个子目录，例如 `viking://user/<user_id>/resources/notes/<项目名>/`（`user_id` 用 `health` 查）；我已经有自己的笔记目录就沿用。值得记的有：重要决定和方针（连同理由）、阶段进展和下一步、中间产物、交付物。我给的文件用 `add_resource` 放进 `viking://user/<user_id>/resources/<项目名>/`，和笔记分开：笔记目录不要拿来做 `add_resource` 的目标，笔记也不要写进 `add_resource` 导入的目录，那里重新同步时会删掉不属于源文件的内容。不存日常对话（插件会自动保存），不存密钥，不主动扫描或上传我没提到的文件。写完读回确认。
- 继续一个项目时，先看它笔记目录里的决定、进展和下一步。新的决定推翻了旧的，就改原来的记录，不要留两份矛盾的说法。
- 一轮里实际用到了 OpenViking 的内容，或者存了东西，在回复末尾用一句话说明：用了哪条背景、存了什么、存在哪里。没用到就不说。
<!-- openviking:end -->
```

用户同意后，写进当前宿主的用户级规则文件。[附录 A](#附录-a各宿主说明) 的「用户级规则文件」一列是常见位置，以宿主实际读取的文件为准：

- 只动标记块之间的内容。已有标记块就替换中间部分，没有就追加到文件末尾，文件不存在就新建。块外的内容保持原样。
- 文件里已有和这段规则冲突的要求（例如每轮都必须检索，或者不许把资料存到外部），先告诉他冲突在哪，按他的决定改。
- 写完读回，确认写进去的和他确认的原文一致、标记块只有一份、块外内容没变。
- 宿主的个人规则只能在应用设置里改，或者写入失败时，把规则给他，请他自己粘贴进去。不确定是哪个文件时，问他，不要猜。

不要把规则写进项目文件。等他回答之后再进入步骤 5，不要在问这个问题的同一条消息里提重启。

## 步骤 5：重启

插件要在宿主重新启动后才会加载。当前宿主已经生效、本次也没有新装插件时，跳过这一步，直接进入[重启之后](#重启之后)。

先用两三行交代现在的状态：连上了哪个服务、导入了什么、协作规则写没写。然后告诉用户三件事：

1. **当前宿主怎么重启和信任 hook**，见[附录 A](#附录-a各宿主说明)的「重启或信任」一列。表里写了重启时要告诉用户的事（例如 Codex 会保存这段安装对话），一并用一句话说清。安装器还装进了其他工具时，加一行点出它们的名字：每个都要各自重启后才生效，具体看安装器输出里的 `下一步：`（英文 `Next:`）。
2. **重启后回到哪里**，看附录 A 的「重启后」一列：
   - 写着「回到原会话」的宿主：告诉他用表里的命令回到**这段对话**，然后发一句「已重启」。第 3 条那句话也给他，作为备用：回到的不是这段对话时，在新会话里发它。
   - 写着「开新会话」的宿主：告诉他开一个新会话，不要恢复这段对话，也不要在这里重新加载插件，表里写了原因的一并说明，并给他第 3 条里的那句话。
3. **开新会话时要发的第一句话**，直接给出可复制的文本。网址用你实际打开成功的那个，尖括号换成实际结果：

```text
已重启。从 https://docs.openviking.net/agents/zh/onboarding.md 的「重启之后」继续 OpenViking 接入。历史导入：<例如「导入了 2 个会话」「已跳过」>；协作规则：<已写入 / 未写>；接下来想做：<他说过的目标，没说就写「先看看上次做到哪」>。
```

说完就停下，等用户操作。

## 重启之后

插件现在应该已经在这个会话里运行。这一段的目的，是让用户用他自己的工作看到已有积累的用处。已经确认过的选择和讲过的说明不要重复。

1. **确认插件在运行。** 当前对话里有 `<openviking-context>` 块，或者 OpenViking 工具可用。调用 `health` 工具（名字可能带前缀，例如 `mcp__openviking__health`、`openviking_health`）。都没有时，见故障排查的「重启后没有召回」。有注入块才说明自动召回在运行；没有相关记忆，可能只是库里还没有相关内容。
2. **补上缺的选择。** 从这段对话或续接消息里确认导入和协作规则是否已经做完。缺了就补做那一步，做过的不要重问。
3. **用一件真实的事展示效果**，按他想要的结果选一种：

| 他想要的 | 怎么做 |
|---|---|
| 接着过去的工作做 | 先用注入的上下文，不够再用 `search`（`mode="context"`）查导入的记忆。说清这项工作要完成什么、上次做到哪、定过哪些判断、还有什么没解决，再给两三个具体的推进方向，指出哪条依据来自 OpenViking、它怎么影响了建议。有多项工作时先让他挑一项。 |
| 保存或复用一份资料 | 按他点名的文件添加后读回，或者读已有的资料回答他一个真实的问题；告诉他存在哪、下次怎么找。 |
| 从现在开始，或者暂时不体验 | 说清以后会怎么积累，请他直接开始一件真实的工作，或者稍后再用。 |

   给出总结和建议后，等他选方向，不要直接动手改代码或推进任务。记忆还在整理时，可以读导入的原对话，但要说明这是读的原记录，不是自动召回。

4. **最多三行收尾**：
   - 已经能用什么、还有什么在后台进行（例如记忆整理）；
   - 在这个宿主上哪里能看到 OpenViking 的作用（附录 A 的「在哪里能看到」）；
   - 以后可以说的话，挑一两条和他相关的：「把 <项目> 的会话导入 OpenViking」「保存这份文档，之后按它继续」「换一个 OpenViking 账号」（按[从哪一步开始](#从哪一步开始)里「更换」的做法处理）。装进了其他 Agent 时提一句：在那边接入同一个账号，就能接着这项工作。
