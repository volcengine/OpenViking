# PostgreSQL + pgvector

Select `storage.vectordb.backend="pgvector"` to store collection metadata,
dense vectors, scalar fields and sparse postings in PostgreSQL. OpenViking
connects through a bounded psycopg2 connection pool; vector search executes
inside the PostgreSQL process. Embeddings are still generated by the configured
embedding provider.

## Setup

Install the optional client dependency:

```bash
pip install 'openviking[pgvector]'
```

Install pgvector **0.8.0 or newer** on the PostgreSQL server, then enable it in
the database used by OpenViking:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
SELECT extversion FROM pg_extension WHERE extname = 'vector';
```

The extension must be installed in the `public` schema. The connection role
needs access to that schema and permission to create collection tables and
indexes, and read/write their data. Collection initialization is serialized
with PostgreSQL advisory locks. Table and index metadata use the shared
`_ov_collection_meta` and `_ov_index_<collection>` catalogs. Use distinct
databases or collection names for independent deployments, and do not reuse an
openGauss collection name.

Set a DSN in the server environment. PostgreSQL DSN options such as `sslmode`
and `sslrootcert` can be supplied here:

```bash
export OV_POSTGRES_DSN='host=127.0.0.1 port=5432 dbname=openviking user=ov password=CHANGE_ME'
```

DSN mode is the default connection method (`dsn_env` defaults to
`"OV_POSTGRES_DSN"`). When the password contains special characters (`@`, `:`,
`/`, spaces, single quotes, etc.), you must escape or percent-encode them
within the DSN string according to the PostgreSQL DSN specification.

### Split-field mode (recommended)

pgvector also accepts split-field connection parameters, aligned with the
openGauss backend. The password is passed via a config field and reaches
PostgreSQL verbatim, requiring no escaping or encoding. String values in the
config file (such as `password`) may use `${ENV_VAR}` references that are
expanded at load time, suiting K8s/container deployments where each field
maps to a separate Secret environment variable.

```json
{
  "storage": {
    "vectordb": {
      "backend": "pgvector",
      "name": "context",
      "dimension": 4096,
      "distance_metric": "cosine",
      "pgvector": {
        "host": "${OV_PG_HOST}",
        "port": 5432,
        "user": "${OV_PG_USER}",
        "password": "${OV_PG_PASSWORD}",
        "db_name": "openviking",
        "sslmode": "require",
        "index_type": "flat"
      }
    }
  }
}
```

Split fields and `dsn_env` are mutually exclusive: both cannot be explicitly
configured at the same time. When no split fields are provided, DSN mode is
used by default, preserving full backward compatibility.

| Aspect | DSN mode | Split-field mode |
| --- | --- | --- |
| Password carrier | Inside the DSN string | `password` field |
| Special-character passwords | Manual escaping/encoding required | Passed verbatim, no encoding |
| Env var expansion | Not supported (DSN lives in env) | `${VAR}` expanded at config load |
| `sslmode` | Configured inside the DSN string | `sslmode` field |

Merge this fragment into the existing OpenViking configuration, keeping the
embedding dimension equal to the vector dimension:

```json
{
  "storage": {
    "vectordb": {
      "backend": "pgvector",
      "name": "context",
      "dimension": 4096,
      "distance_metric": "cosine",
      "pgvector": {
        "dsn_env": "OV_POSTGRES_DSN",
        "index_type": "flat",
        "connection_pool_min_size": 1,
        "connection_pool_max_size": 10
      }
    }
  }
}
```

This is a Cluster-level backend. Account-owned `vectordb` settings currently
accept only `http`, `volcengine` and `vikingdb`.

## Search and index settings

| Setting in `pgvector` | Default | Meaning |
| --- | --- | --- |
| `dsn_env` | `OV_POSTGRES_DSN` | Environment variable containing the connection DSN (DSN mode) |
| `host` | `127.0.0.1` | PostgreSQL host address (split-field mode) |
| `port` | `5432` | PostgreSQL port |
| `user` | `postgres` | Database user |
| `password` | `""` | Database password, passed verbatim, supports `${ENV_VAR}` expansion |
| `db_name` | `openviking` | Database name |
| `sslmode` | `None` | libpq SSL mode (`disable`/`allow`/`prefer`/`require`/`verify-ca`/`verify-full`) |
| `index_type` | `flat` | Exact dense search or native `hnsw` ANN |
| `connection_pool_min_size` | `1` | Minimum connections per adapter |
| `connection_pool_max_size` | `10` | Maximum connections per adapter; must be at least the minimum |
| `m` | `16` | HNSW connections per layer, from 2 to 100 |
| `ef_construction` | `64` | HNSW build candidate list, from 4 to 1000, at least twice `m` |
| `ef_search` | `100` | HNSW search candidate list, from 1 to 1000 |
| `candidate_limit` | `1000` | Candidate budget per modality for sparse/hybrid or time-decay ranking, from 1 to 10000 |

Dense values use full-precision `vector`, with 1–16000 dimensions. Native
HNSW supports at most **2000 dimensions** for this type. For a 4096-dimensional
embedding, keep `index_type="flat"`; the backend does not silently truncate or
quantize it. `halfvec`, binary quantization and IVFFlat are not implemented.

For embeddings with at most 2000 dimensions, select:

```json
{
  "dsn_env": "OV_POSTGRES_DSN",
  "index_type": "hnsw",
  "m": 16,
  "ef_construction": 64,
  "ef_search": 100
}
```

`distance_metric` accepts `cosine`, `l2`, `ip` and `l1`. Results use the
OpenViking convention of higher scores ranking first. Scalar, tenant, ACL and
URI scope filters are compiled to parameterized SQL. HNSW uses strict iterative
scanning to improve recall with filters, but ANN recall and filtered TopK are
not guaranteed; measure recall and p99 with representative filters. Cosine
zero vectors are not included in a pgvector HNSW index.

Cosine search also excludes zero vectors from flat results and dense candidates
in hybrid/time-decay search. Native dense search drops NaN distances after
sorting and pagination: PostgreSQL sorts NaN after all finite distances, so zero
vectors cannot displace eligible results or alter valid pagination. Hybrid
sparse recall excludes them before applying its candidate budget, with a CASE
expression that evaluates the norm only after scalar filtering. Sparse-only
search still accepts these records. Ordinary dense queries serialize the query
vector once and reuse the string for both SQL parameters.

Flat search stays exact even when the table also contains an ANN index. On
reconnect, the configured collection dimension, metric and index type must
match persisted metadata; missing or invalid ANN indexes produce errors.
Changing `ef_search` takes effect on reconnect without rebuilding. Changing
index type or build parameters requires a planned index/collection rebuild.

Sparse terms are stored in JSONB with a posting table. Sparse-only recall uses
positive term overlap; hybrid search unions bounded dense and sparse candidates
and computes complete scores within that union. It does not guarantee global
fused TopK. `sparse_weight` and embedding configuration retain their usual
meaning.

## Directory filter tuning

### Select the search implementation

`pgvector.search_implementation` accepts only `native` (default) and `enhanced`:

- `native` uses community pgvector SQL. PostgreSQL chooses the execution plan.
- `enhanced` uses ByteDance enhanced search, currently implemented through the
  `ov_filtered_knn` envelope-v1 API. Initialization validates extension membership,
  signatures, PostgreSQL version and permissions. Missing capabilities and unsupported
  dense indexes raise errors without automatic fallback. Execution, permission and
  budget errors propagate.

The choice is independent of filters: unfiltered, account, ACL and path queries
all use the selected implementation. Normal account-bound service searches still
add `account_id`; both implementations retain these predicates, MVCC and RLS.
This setting selects query behavior, not the database extension binary, and does
not select or create an index. A database with the ByteDance extension can also use
`native`.

The old `filtered_knn` and `unfiltered_use_native` settings have been removed and
are rejected by configuration validation. Choose `search_implementation` explicitly
when migrating. `filtered_knn_options` remains the enhanced API parameter group and
only applies to `enhanced`. Its `mode="exact"` selects an enhanced algorithm without
changing the search implementation.

Native HNSW scans use `ef_search` (1–1000), rather than enhanced search width,
visit budgets or recovery. Enhanced search also uses the envelope when the adapter
receives `None` or `{}`.

For bounded recovery experiments, set `search_implementation="enhanced"`, fix
`search_width=2000`, set `recover=true`, and compare `max_graph_visits` of
100000, 200000 and 400000 with the same heap and memory budgets. Recovery
disables the heuristic stop but remains bounded by total visits, heap fetches
and memory. A visit limit does not guarantee a particular recall.
Discovery runs only during adapter initialization in `_connect()`. Its result is
cached and copied into each Collection. `native` does not probe enhanced capabilities.
Recreate the adapter and its Collections after upgrading the database extension or
changing the implementation, typically by restarting or rolling restarting the service.
Creating or replacing physical pooled connections and reloading a Collection do not
refresh the selected implementation or rediscover capabilities.

The current capability supports PostgreSQL 17 and full-precision HNSW vectors
up to 2000 dimensions. Dense, hybrid and time-decay share its candidate hook;
sparse-only queries retain the existing posting path. Candidates and fields are
read in one SQL statement. Per-query DEBUG logs include route, stop reason and budget
statistics, including empty results.

```json
{
  "index_type": "hnsw",
  "search_implementation": "enhanced",
  "filtered_knn_options": {
    "mode": "adaptive",
    "exact_threshold": 1000,
    "search_width": 100,
    "max_graph_visits": 20000,
    "max_heap_fetches": 200000,
    "eligible_memory_limit": 67108864,
    "recover": false
  }
}
```

`eligible_memory_limit` accepts 1 MiB–4 GiB on a 64-bit extension, in bytes
(`4294967296` for 4 GiB); the default remains 64 MiB. This is a per-request
aggregate checkpoint budget, allocated on demand. Temporary overshoot is possible;
SPI executor memory and the final JSON envelope are not fully covered.
32-bit extension builds retain a 1 GiB maximum.

Options are strictly validated. `mode="exact"` forces exact candidate search;
`exact_threshold=0` selects ANN for nonempty eligible sets. Search width is
raised to the requested candidate budget. ANN may return partial qualified
results with an explicit stop reason. Eligibility currently scans the complete
filtered set; measure recall, scan cost and p99 before enabling in production.

Enhanced dense pagination requests `candidate_k = limit + offset` and sets
`search_width = max(configured width, candidate_k)`. The configured width is a
starting width, not a request ceiling; both the candidate budget and effective
width have a hard maximum of `100000`. Above that limit the adapter raises
`ValueError` before executing the query, without truncating pagination or falling
back to native SQL. Explicit exact mode has the same limit. Direct extension
calls with an excessive `candidate_k` raise SQLSTATE `22023` with
`ov_filtered_knn: candidate_k must be between 1 and 100000`.
These extension budget limits do not apply to native SQL routing, and `limit=0`
still returns an empty result. Within valid budgets, insufficient ANN candidates
can produce fewer than `limit` rows or an empty page. Stop reasons are logged
at DEBUG level rather than exposed as additional `SearchResult` fields.

For normalized URI scopes on large collections, evaluate a composite B-tree
expression index over tenant and path. See
[pgvector directory filter indexes](26-pgvector-directory-filtering.md)
for SQL, level/depth semantics, million-row results and rollout boundaries.
This index requires manual evaluation and deployment; the backend does not
create it automatically.

## Data and deployment boundaries

Upsert batches are transactional, including sparse postings; a failed batch
rolls back. Collection data and index metadata survive restarts. PostgreSQL
replication, backup and PITR can protect these database records when configured
by the operator.

TTL writes and native BM25/full-text search are not supported. The `content`
field is stored in PostgreSQL (the service write path retains its existing
1 MB content payload limit), while grep uses OpenViking's filesystem
fallback. Collection DDL is performed during initialization; this backend does
not provide automatic schema migrations or automatic repair of damaged indexes.

Switching the backend does not import existing local vectors. Create a new
collection and reindex resources, or perform a separately verified migration.
Keep the old vector store until the replacement has been checked.

Resource files, queues, account/task stores and PathLock remain independently
configured. Sharing pgvector alone does not make local workspaces safe for
multiple OpenViking processes. Follow the [deployment guide](03-deployment.md)
for shared storage and coordination; PostgreSQL PathLock is a separate feature.

## Integration tests

Tests create randomly named collections and remove them afterwards. Use a test
database with pgvector enabled:

```bash
export OV_PGVECTOR_TEST_DSN='host=127.0.0.1 port=5432 dbname=ov_test user=ov'
pytest tests/storage/test_pgvector_adapter.py
```
