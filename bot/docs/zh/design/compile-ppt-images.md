# PPT 图片输入与 Compile 请求期限

## 需求与边界

用户要求压缩图文 PPT 中的图片、移除未经端点验证的统一拒绝门槛，并排查 Compile 超时。验收材料经用户授权使用合成 PPT，规模为 15 份各 101 页。用户随后要求因磁盘空间不足停止完整测试，按现有证据和定向回归拆分提交；本文不代表客户原材料或全量 Wiki 验收通过。

以下实现参数由 AI 提出，实现与测试由 AI 完成，仍需维护者评审；不把这些参数归为用户指定的要求。

## 实现与取舍

- 原始资源字节保持不变。读取大于 512 KiB 的静态图片时，沿用现有预览的最长边 2048 像素，生成 JPEG 质量 85 的模型用图；只有更小时才采用。小图、动画与转换后更大的图片保留原件；先校正 EXIF，透明背景铺白。来源 URI、SHA256 始终基于原图，模型输入 MIME、字节数基于实际发送内容。
- 删除多图读取、Compile 分批与 AgentLoop 中统一的 3.75 MiB、4 张图拒绝或静默丢弃门槛。格式、身份、权限和现有 512 MiB 单资源保护保留。分批字符数是工作集软目标，真实端点错误仍进入已有失败路径。
- 删除 Compile 单次请求和整个 assignment 外层的额外墙钟期限，避免把共享槽位排队与 provider 重试算作一次 HTTP 超时。底层客户端继续使用配置的 VLM HTTP timeout；取消、无进展检测、重试次数和 agent 迭代约束保留。
- 诊断记录模型用图数、字节数、实际配置的 HTTP timeout 与错误类别，不记录图片正文或密钥。

压缩增加 CPU 与短时解码内存，JPEG 和缩放可能影响细字、图表。沿用已有 Pillow 依赖，通过线程卸载解码，不增加部署组件。移除静默丢图后会处理以前跳过的来源，模型调用量可能增加。字节减少不等于 token、费用或延迟同比减少，端点能力也不应替换成另一套全局硬编码。

## 已有实测与待验证项

- 标准 AnyDoc 解析与入库完成 15/15 份合成 PPT，共 1,515 页图片和 435 份正文 Markdown；1,515 个正文检查点及全部原图 SHA256 已核验。
- 105 张图超过旧的 3,932,160 字节门槛。真实火山 DeepSeek Map 已覆盖 1,950 个来源片段；图片进入原生模型调用。独有图片内容中，1,510/1,515 个审计码精确读出，另外 5 个非验收检查点有 OCR 差异，不能声称逐页完美识别。
- 唯一原图共 572,361,756 字节，准备的模型用图共 142,242,950 字节，减少 75.15%。这是语料图片字节统计，不是所有网络流量或模型费用。
- 小样完成正文、图片事实、引用及导航检查。15 份材料的最终 Wiki 未完成验收；测试已停止，未继续下载沙箱镜像或启动更大测试。
- 定向回归覆盖大图压缩后的 MIME/原图身份、保留所有请求图片、批次引用边界和 provider 排队；HTTP timeout 的配置传递使用已有回归。

输出校验、重试和 Reduce 缺陷另行提交，不把客户侧模型 429 配额问题作为产品修复。
