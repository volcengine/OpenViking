# 个人终端与 Studio 统一实现方案

讨论背景、最新确认及当前实现边界统一记录在[项目背景与已确认决策](all-ov-studio-background.md)。本方案中的阶段目标不等于交付状态；后续确认覆盖早期表述，尤其是火山 ROOT 管理跳转已改为产品目标保留、本轮暂缓。

状态：阶段 0 与私有化 API Key 登录已实施；验证结果与限制见[阶段验收记录](all-ov-studio-stage-0.md)。日期：2026-11-02。目标分支：`feat/all_ov_studio`。下文保留完整目标，未完成模块不代表当前可用。

进度补充（2026-11-03）：公共登录、密码恢复与邀请页面及路由已交付。官方 `/login` 先展示企业登录 / API Key 选择，私有化默认 API Key 且先选中火山托管服务；真实账号 API 与邀请完整流程仍待联调，见[UX 迁移记录](all-ov-studio-ux-migration.md)。

入口分层补充：部署、服务、登录入口、角色与页面区域的枚举已集中，版本配置由启动入口选择，认证表单不再直接判断版本，见[入口目录与枚举说明](studio-entry-architecture.md)。最新讨论提出火山 ROOT 也应进入管理后台，但用户要求本次暂不处理该跳转，当前未改变其行为。

## 1. 目标与依据

在现有 `web-studio` 中统一个人终端与 Studio，共用工作台、管理组件和业务模型，以部署配置、登录适配和服务能力表达版本差异。官方域名部署提供火山版；随开源 OpenViking 部署的 Studio 默认提供私有化版。用户自部署并绑定自己的域名，不会因此变成火山版。

依据与优先顺序：用户在本次讨论中明确确认的规则 > 已确认的最新评审评论 > 当前需求正文 > 动态原型中的示例行为。尚未明确的评论保留为待定，不直接变成实施要求。

- [需求正文与评论](https://bytedance.larkoffice.com/wiki/GGchwdV0Qi4HNFkXEK9c6NXZnCe)：已读取全文及当时可见的 23 条未解决评论和返回的回复。
- [动态原型](https://bytedance.larkoffice.com/page/Zvt9m8AvCdhsLHaNUuOc2Z2Unwg)：已走查企业登录、账号切换、Agent 接入、私有化 User/ROOT 登录、应用连接和管理后台；并非所有页面和异常分支均已走查。
- [现有工程结构](./frontend-structure.md)、[管理态拆分](./admin-workbench-refactor.md)、[当前接口权限](./permission-matrix.md)：作为复用和兼容依据，不代表托管接口已完成联调。

原型是形态和交互参考，不是后端权限或接口已经具备的证明。其演示数据、安装地址、Key 和模拟登录逻辑不进入正式实现。

## 2. 已确认的产品规则

### 2.1 部署版本与连接服务

| 部署形态 | 登录入口 | 可连接服务 | 管理后台 |
| --- | --- | --- | --- |
| 官方火山版 Studio | `/login` 选择企业登录或 API Key；邀请和密码恢复保留公共页面 | 火山托管服务；API Key 页隐藏服务选择与固定地址 | 当前未开放；火山 ROOT 进后台为最新产品目标，本轮暂缓实现 |
| 开源私有化 Studio | API Key 连接服务，默认火山托管、自部署排第二 | 火山托管地址只读、自部署地址可输入 | 连接自部署服务时按实际角色授权 |

部署版本决定产品入口；当前连接决定接口协议和合规提示；服务端确认的身份决定权限。三者不能用同一个 `isCloud` 或域名判断替代。私有化 Studio 连接火山不启用企业邮箱登录；火山 ROOT 的识别、跳转及管理接入另行推进，本轮不改变既有行为。

### 2.2 角色与落地页（用户已确认）

| 角色 | 默认落地 | 个人工作台 | 管理能力 |
| --- | --- | --- | --- |
| ROOT | 管理后台 | 无个人目录，不能把 Root Key 当作数据 User | 服务级及允许的跨数据空间管理 |
| Admin User | 个人工作台 | 有自己的目录、会话、经验及获授权共享数据 | 当前数据空间的成员、用户组、规则等已授权管理能力 |
| 普通 User | 个人工作台 | 自身与获授权数据 | 不提供管理后台 |

- ROOT 不再提供“默认进入个人工作台”的偏好。旧偏好不能覆盖新规则。
- ROOT 如果要使用某个 User 的工作台，必须显式切到该 User/Admin 的有效数据身份；不默认选择管理员，不自动获取或重置成员 Key。
- Admin 的“进入管理后台／返回工作台”切换保留其数据身份，管理范围固定在自身数据空间。不能通过改 URL、前端下拉框或请求头跨空间。
- “Admin 能管理当前数据空间”不等于每个管理端点都已开放，也不等于能浏览其他成员的私有记忆。
- 官方火山工作台当前仍不挂载管理后台。最新确认的目标是火山 ROOT 进入后台，但用户已要求暂缓这个跳转；此处记录当前实现，不代表永久产品限制。
- `trusted`、`dev` 等已有认证模式的协议与 API Key 模式分开处理：受信传输凭据不能被简单当作当前个人身份。保留现有协议测试，实施入口变更前核对有效身份；不得以新 UI 为由静默关闭现有认证模式或扩大权限。

### 2.3 版本差异与本期范围

| 能力 | 官方火山版 | 私有化版 |
| --- | --- | --- |
| 目录、文件预览编辑、Experience、任务、技能、VikingBot/终端 | 共用业务实现，按接口能力启用 | 共用业务实现，按接口能力启用 |
| 企业登录、邀请、密码恢复 | 提供，依赖托管账号服务 | 不提供 |
| API Key 添加／切换 | 邮箱账号下保存或本地保存，取决于登录方式 | 本地连接与凭据管理 |
| API Key 自助重置 | 仅邮箱身份，依赖托管接口 | API Key 账号菜单不提供自助重置；后台管理成员 Key 是另一种操作 |
| 合规提示 | 按当前火山身份的邮箱绑定状态展示 | 连接火山时展示；连接自部署服务时不展示 |
| AI 提炼标签 | 保留 | 保留 |
| 文件删除 | 本期置灰并说明预留 | 自部署服务上按写权限提供；连接火山时遵守托管限制 |
| OVPack 导出／导入 | 导出不提供；导入后续支持，本期无入口 | 复用现有 Studio 能力，仍需目标服务支持 |
| User 侧飞书机器人 | 本期标下一期 | 本期 P1，依赖 User 侧服务接口 |
| OAuth | 本期无入口 | 接入 Agent 流程中提供，旧验证链接继续兼容 |
| 上下文数据 | 菜单标下一期 | 复用统计组件，仅当前 User 范围 |
| 网关 | 无管理入口 | 管理区保留“下一期”入口；不扩大为本期网关开发 |

首批优先级按 11 月 2 日评审：登录与账号、快速开始与 Agent 接入、目录工作台、文件预览编辑、Experience 看板、资源导入与定时同步、compile/资源任务、添加 Skill 为 P0。管理后台改版、检索改版、快照、OVPack、会话浏览、飞书机器人等为 P1。已有权限边界和可用能力的回归不因 P1 而延后。

## 4. 实现结构

### 4.1 部署配置与能力策略

新增启动前解析的 `StudioDeploymentConfig`（名称为方案建议），至少包含：

```ts
type StudioEdition = 'volcengine' | 'self-hosted'

interface StudioDeploymentConfig {
  edition: StudioEdition
  hostedApiBaseUrl?: string
  accountServiceBaseUrl?: string
  helpUrl?: string
}
```

开源构建默认 `self-hosted`；官方部署显式注入 `volcengine`。允许同一代码通过构建默认值或宿主运行时配置部署，配置在应用启动前校验，不根据是否有公网域名自动切换。配置仅含非敏感元数据，不含用户凭据。部署配置不是授权凭证。

STG 的 `/workbench-stg/` base 在启动时确定环境，默认官方组合；浮动控件用标签页 `sessionStorage` 选择预览版本，整页重载回该 base 下的 `/login`，托管地址始终保持 STG。生产忽略预览选择，官方生产仍需显式 `VITE_STUDIO_EDITION=volcengine`；构建和检查命令见[阶段记录](all-ov-studio-stage-0.md#部署配置)。

功能策略集中返回：可用、无权限、服务未支持、下一期、能力未知，并携带呈现方式（隐藏／禁用／解释页）。路由、导航、按钮使用同一份判断。接口写权限仍由服务端执行；一个健康检查成功不代表所有写操作开放。

建议在 `app` 下放部署配置与页面装配，在 `connection` 中放身份、登录和鉴权协调，在现有服务能力模块中维护功能策略。避免在每个业务组件散落版本判断。

### 4.2 账号、身份与请求

明确三个对象：登录账号（邮箱或 API Key）、当前数据身份（服务／库、数据空间、User）、当前管理范围（服务或数据空间）。UI 中“账号”不再与后端 Account 混用；Account 展示为“数据空间”。

新增托管账号适配契约，覆盖登录／退出、Session 恢复、邀请查询及接受／拒绝、密码恢复、身份列表、Key 查看／重置、附加 Key 的保存／移除。具体 HTTP 路径与 Cookie/Token 方式以接口合同为准，不在前端假设。

切换账号或 User 时：确认切换目标有效 → 取消旧身份请求和流式连接 → 隔离或清理对应查询缓存 → 切换请求上下文 → 挂载新视图。缓存至少区分服务、登录账号、数据空间、User 和管理／数据作用域。编辑中的内容提示保存或放弃后再切换。

邮箱登录的密码不持久化；Session 按托管约定恢复。API Key 账号沿用加密本地存储，兼容受限浏览器的仅内存模式。移除账号不等于撤销 Key；退出不调用 Key 重置。退出后本地是否保留可恢复账号及是否要求重新验证，在阶段 1 明确，不能把本地断开称作服务端 Key 吊销。

### 4.3 页面与路由

- 公共流程：登录、邀请、密码恢复、添加账号；表单共用，登录与添加身份保留不同返回路径。
- 工作台：顶栏 + 目录树 + 单内容区 + VikingBot/终端；任务、导入等需要大面积操作的页面进入整页模式。
- 管理后台：复用顶栏，使用管理导航；不挂载个人目录树、个人任务和聊天面板。
- 路由继续薄装配；旧 `/home`、`/filesystem`、`/compile`、`/skills`、`/sessions` 等链接按目标功能重定向或兼容，保留必要的 URI、任务 ID、查询参数。
- 登录成功优先恢复合法、可访问的业务深链；ROOT 的个人工作台深链转管理入口，普通 User 的管理深链转工作台或无权限说明，不先挂载受限页面。
- 旧连接设置入口迁到账号菜单后，仍保留修复无效地址／Key 的路径。不可达服务不能使配置修复入口也不可用。
- 桌面三栏；平板按需收起右栏；手机以目录抽屉、全屏内容与聊天／终端面板切换呈现。任务表保留关键字段和独立详情，避免把三栏等比缩小。

### 4.4 业务复用

目录按服务端 URI、目录类型和权限生成视图，不通过名字相似猜测权限。内置目录清单作为显式模型；具体清单待接口与设计对齐。L0/L1 与“目录内容”分别对应摘要文本和子项卡片；Experience 增加专属看板，不在 User 根目录重复放看板。

任务分为任务定义／调度配置、执行记录、执行步骤及日志。compile、资源导入分别适配现有接口，前端使用共同呈现模型；在接口确认前不假设周期执行复用同一任务 ID。其他任务类型保留可扩展适配位置，但不挤入首批范围。

管理与工作台共享的任务表、统计卡片等抽出不携带默认凭据的组件和模型，由各自页面传入范围、数据和可执行操作。遵守现有 workbench/admin 不互相导入的规则；不要为了复用把管理请求带进个人工作台。

## 5. 分阶段改动与验收

阶段代表可独立审查的实施顺序，不是未经确认的日期承诺。每阶段拆成小批提交，保持可运行。阶段 1 的接口确认应尽早启动，不能拖到 UI 全部做完才开始。

### 阶段 0：部署版本、角色入口和能力边界

**改动**：增加部署配置；改造入口决策与路由边界；ROOT 固定进管理后台；Admin 保留工作台及本空间管理；普通 User 禁止进入后台；落地功能矩阵。主要涉及 `app/router`、`app/layouts/studio-feature-boundary.tsx`、`connection/lib/studio-mode.ts`、`platform/access/management.ts`、`platform/access/features.ts`。

**验收**：两种部署配置可启动；三种角色的首次访问、刷新、深链和角色未解析状态正确；官方版不挂载管理页面；ROOT 不发个人目录请求；Admin 不显示跨空间或服务级操作；既有 trusted/dev 协议回归通过。

**依赖**：无托管业务接口依赖即可先建立配置与策略测试。角色探测仍沿用服务端真实结果。

### 阶段 1：登录、账号切换与凭据生命周期（L1–L10、U1/U2/U6/U7）

**改动**：私有化登录默认火山托管、自部署排第二，托管地址只读且要求协议勾选，自部署地址可编辑且无协议勾选；火山版先选择企业/API Key 登录，API Key 页隐藏服务和地址，显式登录页可返回选择页。继续联调邀请、密码恢复及统一账号菜单、顶栏身份、Key 弹层，迁移现有连接记录。复用 `connection` 验证器和存储，在其内部增加托管账号适配。

**验收**：私有化 User/Admin/ROOT 三条真实登录链路正确；邮箱和 API Key 区分菜单与身份选择；邀请只有接受后才新增可用身份；Key 失效、Session 过期、拒绝邀请和账号切换无数据串用；旧本地连接可迁移且失败可恢复；敏感凭据不进入 URL 或日志。

**依赖**：托管 Session、邀请、身份列表、Key 服务、协议文案。接口未就绪时可用开发 mock 验证页面，但官方发布验收必须接真实服务，mock 不作为已交付能力。

### 阶段 2：统一工作台与个人终端（D1–D6、G1/G2、U4、X1）

**改动**：工作台三栏外壳、目录树单选导航、单文件内容区、VikingBot/终端右栏、快速开始、帮助、搜索入口、导入入口、合规提示和 AI 提炼标签。移除工作台功能侧栏及多文件页签，保留管理导航。目录内容卡片 D4 可随本阶段建设，按 P1 验收。

**验收**：从目录进入文件、会话、技能和经验时内容切换正确；刷新可恢复合法路径；聊天和终端使用当前数据身份；自部署连接不显示火山合规提示；切回火山恢复；桌面／平板／手机主流程可操作；未保存编辑和身份切换有明确处理。

**依赖**：基础身份和文件能力；Bot 服务能力。快速开始使用真实接入指令，不能复制原型中的占位安装脚本。OAuth 的接入方式按阶段 5 的服务能力逐步接上。

### 阶段 3：P0 数据操作、Experience 和统一任务中心

**改动**：

- E1：复用文件预览／源码／编辑，调整工具栏；火山删除禁用，自部署按权限和确认流程执行。
- D9：Experience 目录列表、经验文件应用效果／来源追溯／测试页签；补齐指标查询与空态。
- T1/T2：全页本地／网页导入，其他数据源按能力授权；每天／每周／不更新的调度配置与操作。
- T3/T4：compile 和资源导入统一列表、筛选、详情、每次执行记录、配置及可执行操作；只呈现本期支持的任务类型。
- C2：Skill 文件、zip、GitHub 目录导入，name/description 校验，“只有我／团队”受真实写权限约束。
- D8 的新编译入口优先接通：选中目录 → VikingBot 的 Wiki／知识视频／日报入口 → 配置确认 → 任务中心 → 查看产物。该入口属于 P1，但与 compile 闭环一起交付更完整。

**验收**：真实执行“导入 → 查询任务 → 查看目录”和“编译 → 查看执行 → 打开产物”；任务不能通过伪造发起人获得操作权；周期任务历史可正确关联；Skill 三类输入有成功与失败路径；Experience 指标、轨迹和测试内容来自真实接口，缺数据不生成虚假统计。

**依赖**：数据源开放范围、上传限额、调度变更接口、执行 ID 关联、取消／重试能力、Experience 指标及测试接口、团队写权限。P0 发布必须逐项记录真实可用性，不能仅展示入口。

### 阶段 4：管理后台完善与共用组件（D7、A1–A14）

**改动**：优先沿用现有管理页面；按数据空间与服务级分组补齐导航、范围提示、数据看板、成员／组／策略、目录权限和抽取规则、配置／模型、组件监控、任务监控、请求日志。Bot 后台取消新增入口；网关标下一期。Admin 的页面和动作按已授权能力裁剪。

**验收**：ROOT 可管理服务与选择数据空间；Admin 仅管理自身数据空间，不能切换服务级管理目标；后台任务和日志不会泄露其他成员的个人记忆；切换空间后表格、统计和缓存同步切换；模型、成员和 Key 的高影响操作使用既有确认与服务端校验。

**依赖**：ROOT 对资源 ACL 的管理与数据身份要求需适配，不能直接把 Root Key 发到数据接口；管理员任务修改／取消、日志过滤需后端支持；全局与空间级配置字段逐项核对。若排期紧，先交付功能正确的现有样式，再做视觉对齐。

### 阶段 5：其余 P1 体验与扩展能力

**改动**：检索弹层与筛选（F1）、快照对比和回滚（E2）、OVPack（E3）、技能和会话目录浏览（C1/M1）、语言主题（U3）、OAuth 接入（U8）、个人上下文数据（U9）、User 侧飞书机器人（G4）。已有语言主题和快照能力在前面阶段保持可用，不等此阶段再恢复。

**验收**：检索限时和错误恢复、快照回滚生成新版本、OVPack 目标目录和冲突策略、会话删除说明、OAuth 当前身份授权、机器人创建／编辑／更新凭据／停用／移除及使用详情，均按支持的版本和真实接口验证。火山后续能力维持文档规定的隐藏或下一期状态。

**依赖**：托管放行、User 侧 Bot API 和 OAuth 能力。User 侧飞书机器人是私有化本期 P1，接口可用后可提前穿插实施，不要求等待全部其他 P1 完成。

### 阶段 6：双版本联调、迁移与发布验收

**改动**：补齐真实服务联调、旧路由和本地配置迁移、构建与部署配置示例、使用文档及回归记录。官方版和开源版使用同一代码版本，分别验证部署产物及入口。

**验收**：身份、能力、业务和设备矩阵通过；官方域名与开源服务内嵌路径分别验证刷新和资源路径；产物不带 demo 数据／凭据／接口；完成回退演练。回退同时考虑静态资源、配置版本与本地存储迁移，不能仅假设切回旧页面即可。

**发布边界**：此方案不执行部署、远端推送或上线。实际发布按后续明确的目标环境推进。

## 7. 验证与完成标准

测试围绕真实风险，不以组件实现细节为目标：

- 部署 × 服务 × 登录 × 角色：官方邮箱/API Key；私有化接火山；私有化接自部署 ROOT/Admin/User；现有 trusted/dev 兼容。
- 权限：ROOT 不访问个人数据，Admin 不跨空间，User 管理深链受限；切换后无旧请求、旧凭据和旧缓存泄露。
- 生命周期：首次进入、刷新恢复、过期退出、邀请回跳、账号移除、连接失败修复、存储不可用及迁移失败。
- 业务：导入／编译任务闭环、周期执行关联、文件修改、经验查看、Skill 导入；扩展功能按实际支持矩阵验收。
- 响应式：建议至少覆盖桌面 1440px、平板 768px、手机 390px，并验证键盘导航与抽屉焦点。

每批改动运行相关测试；阶段集成时运行 `npm test` 和 `npm run build`，遵守架构及国际化检查。重复测试仅在新改动、失败或未解决风险出现时扩大范围。

验收记录分开标记：本地单测／构建、mock 交互、浏览器真实服务、CI、部署后检查。缺少后端的功能保持“前端就绪／待联调”，不得计为发布完成。

## 8. 首批实施建议

先实施阶段 0，并在阶段 1 先完成已有 API Key 真实链路；同时核对托管账号接口。随后完成阶段 2 的统一外壳，再将阶段 3 按文件与经验、导入与技能、任务与编译拆成可审查批次。

首批可评审结果应是：同一份代码可分别启动两版入口，ROOT/Admin/User 去向正确，私有化真实账号能进入统一工作台，托管差异有清晰适配契约。后续以完整业务闭环推进，不以页面数量衡量完成度。
