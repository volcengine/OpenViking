## 2. 部署、服务和登录入口分别建模

“域名部署”在这轮产品讨论中指官方火山部署。开源用户给私有化 Studio 绑定自己的域名，仍然属于私有化版。版本由显式部署配置决定，不根据 hostname 猜测。

| 维度 | 当前枚举 | 含义 |
| --- | --- | --- |
| 部署版本 | `StudioEdition`：`self-hosted`、`volcengine` | 决定产品入口和支持范围 |
| 连接服务 | `ServiceProvider`：`opensource`、`volcengine`、`unknown` | 决定连接的服务及协议能力 |
| 登录方式 | `AuthMethod`：`email`、`api-key` | 用户采用的认证交互方式 |
| 具体登录入口 | `LoginEntry`：`email`、`volcengine-api-key`、`openviking-api-key` | 区分两种 API Key 所连接的服务 |
| 页面区域 | `StudioSurface`：`auth`、`workbench`、`management` | 认证、个人工作台、管理后台 |
| 连接身份 | `ConnectionRole`：`root`、`admin`、`user`、`unknown` | 从服务验证结果取得的角色 |
| 服务认证协议 | `ServerAuthMode`：`api_key`、`trusted`、`dev`、`oidc`、`ldap` | 服务端协议；不与 UI 登录方式混用 |

开发、测试、生产属于发布环境，不等于产品版本、用户角色或权限。

### 最新确认的登录组合

| Studio 部署 | 默认入口 | 登录切换与服务选择 | 地址规则 |
| --- | --- | --- | --- |
| 官方火山版 | 企业登录 / API Key 选择页 | 分别进入 `/login/email`、`/login/api-key`，均可返回选择页；不出现服务选择 | 火山服务地址固定，API Key 页不展示地址 |
| 开源私有化版 | API Key 登录 | 默认火山托管服务，自部署 OV 服务排第二 | 火山地址只读；OV 地址可输入 |

两种部署中的火山 API Key 都是连接火山服务。私有化版连接火山，不会因此切换为官方版或自动开启邮箱账号体系。自部署 OV API Key 入口只在私有化版出现。

官方邮箱/API Key 使用企业服务协议；私有化连接火山使用个人服务协议并要求勾选，连接自部署服务不显示协议勾选。个人协议尚待发布，隐私政策 URL 待用户提供，页面明确标注待补充，不编造链接。协议地址见[UX 迁移记录](all-ov-studio-ux-migration.md)。

STG 默认进入官方组合，浮动控件允许在当前标签页预览私有化版；切换会重新加载完整应用并回到带 Vite base 前缀的 `/login`，两种预览的托管地址均保持 STG。生产忽略预览选择，源码默认私有化；官方生产需显式配置 `VITE_STUDIO_EDITION=volcengine`。配置及检查方法见[阶段记录](all-ov-studio-stage-0.md#部署配置)。

邮箱、忘记密码、重置密码、邀请页面保留公共路由，方便页面联调及链接兼容。私有化版可以访问这些页面，不代表它已支持邮箱账号服务。

## 3. 角色边界及暂缓事项

用户按最新评论确认：

| 身份 | 产品入口与权限规则 |
| --- | --- |
| ROOT | 直接进入管理后台；ROOT 本身不作为个人数据 User 使用 |
| Admin User | 有自己的个人工作台，以及当前数据空间内获授权的管理能力 |
| 普通 User | 只有个人工作台及自身或获授权的数据能力，不提供管理入口 |

Admin 的管理范围不扩展为跨空间 ROOT 权限，也不意味着可以读取其他成员的私有数据。角色来自有效服务端身份；不能通过 Key 内容、登录方式、前端选择项或修改 URL 推断或授予角色。

以上规则已先落实到私有化连接自部署 OV 的 API Key 链路。ROOT 要进入某个 User 的工作台时，需显式切换到有效的 User/Admin 数据身份，不能自动挑选成员或重置其 Key。

**火山 ROOT 跳转暂缓。** 用户随后明确火山 API Key 也可能对应 ROOT 或 User，期望 ROOT 进后台、User 正常进入工作台；在讨论角色识别接口时，又确认“先不用管这个跳转了”。因此，火山 ROOT 进后台保留为产品目标，本轮不改其跳转、角色识别和管理接入。当前官方版仍保留管理入口关闭的既有实现，不能将它解释为永久不支持 ROOT，也不能宣称火山 ROOT 已完成联调。

## 4. 样式范围与登录页面要求

用户要求沿用 `ov-workbench` 的 UX 组件风格，将主题色、按钮、输入框、登录布局及上下文布局适配进 Studio。当前范围是登录及连接相关页面、进入后的文件系统页面；没有要求同时重做所有业务模块。

- 沿用紫蓝主题及 `#5252ff` 主色，并适配 Studio 深色模式。
- 保留现有 Studio 技术栈，不因参考组件使用 Arco 就迁入整套依赖。
- 同时考虑桌面、平板、手机布局，以及键盘焦点和操作可达性。
- 用户指出 `/login` 仍展示工作台内的“添加配置”后，要求恢复原先完整的登录路由。公共认证页需独立于已连接工作台显示，已有连接或离线连接不应遮住登录页。

用户明确接受“先补齐页面与路由，保留双版本规则”，真实账号接口后续联调。已补齐 `/login`、`/login/email`、`/login/api-key`、`/forgot-password`、`/reset-password`、`/invite`，并保留 `/onboarding` 的兼容跳转。

API Key 沿用真实验证及连接保存链路。邮箱、密码恢复和邀请目前只提供页面、前端校验及服务不可用状态；不伪造登录成功、发信、会话或邀请接受。邀请注册、接受、拒绝等完整流程仍未交付。详情见[UX 迁移记录](all-ov-studio-ux-migration.md)和[设计约定](../DESIGN.md)。

## 5. 目录和组件解耦方向

用户担心部署、服务、登录和角色维度增加后，分支判断散落到所有组件；明确要求枚举清楚，并“尽量做到从入口就分层，不要渗透到各处都是加判断”。

当前采用共同业务模块配合入口配置的方式：启动时选择部署配置，入口组装页面并注入登录候选、地址规则和默认落点；业务组件消费配置、能力或权限结果。仅在接口协议、认证生命周期或业务流程确实不同的地方引入适配，不复制整套工作台，也不为每个差异制造一层空转组件。

当前主要结构如下，省略无关文件和测试：

```text
web-studio/src/
├── platform/
│   ├── studio-contract.ts       # 部署、服务、登录、角色等稳定枚举
│   ├── deployment/
│   │   ├── config.ts            # 原始部署配置的统一读取入口
│   │   ├── editions/            # self-hosted / volcengine 配置
│   │   └── experience.ts        # 启动选择与连接准入
│   ├── connection/             # 连接契约、纯配置规范化与数据凭据提示
│   ├── entry/                  # 路径与默认落点
│   └── access/management.ts     # 管理能力策略
├── app/
│   ├── composition/auth-entry.tsx
│   ├── layouts/
│   ├── providers/
│   └── router/
├── features/
│   ├── auth/                   # 公共认证、密码恢复、邀请界面
│   ├── connection/             # 生命周期、连接、凭据和身份流程
│   ├── workbench/              # 文件系统、经验、任务等工作台业务
│   ├── admin/                  # 成员、组、规则、配置等管理业务
│   ├── oauth/
│   └── resource-acl/
├── routes/                     # 薄文件路由
├── shared/                     # 基础 UI、通用模型、样式、传输与工具
├── assets/
├── gen/ov-client/
└── i18n/
```

已实现 `main.tsx → initializeStudioExperience → edition 配置 → AuthEntry → 认证页面` 的入口链路。`ApiKeyLogin` 和 `PublicAuthPage` 接收组装后的配置，不自行判断部署版本。架构检查限制平台层反向依赖及业务层直接读取原始部署配置。

本轮 CR 后已增加连接业务操作、临时身份验证模型，并将认证页面交还真实路由；见[连接与路由重构记录](studio-connection-refactor.md)。后续已落地 `features/auth`、独立连接控制模块、业务只读/操作接口，以及能力规则的明确归属；见[生命周期与认证模块拆分](studio-lifecycle-auth-refactor.md)。文件系统内部模型及剩余协议调用接口仍逐步迁移。代码位置、依赖及枚举详情见[入口分层说明](studio-entry-architecture.md)。
